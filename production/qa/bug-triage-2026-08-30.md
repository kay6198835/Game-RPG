## 🔴 P0 — THE PROJECT DOES NOT COMPILE AT HEAD (blocks everything else)

**New bug, filed as `production/qa/bugs/BUG-064.md`.** This supersedes every other item in this
report until it is fixed — no smoke check (kiểm tra khói), no manual QA hand-off, and no other bug
status below can be *confirmed* by running the game; several statuses below are inferred from
source reading only, because Play Mode cannot currently be entered.

The refactor that CLAUDE.md's 2026-08-28 changelog credits with fixing BUG-042/043/044/046/033/NEW-2
(deleting `EntityStatsSO.cs` and `EntityWeaponMelee.cs`, removing `EntityFindTarget`, restructuring
`Entity.cs`/`EntityData.cs`) was **not finished** — it left dangling references across the Entity/AI
stack that fail to compile:

1. `EntityData.cs:8` still references `EntityStatsSO` — the type was deleted this week.
2. `Entity.cs` — the `EntityData data` field was removed, but `LoadEntity()`, `LoadState()`, and
   `SetDataEntity()` still reference `data`.
3. `Entity.Data` (the public getter) was removed, but is still called from `EntityInput.cs:81,83`,
   `EntityAttack.cs:68`, and `EntityEffectStats.cs:20`.
4. `EntityInput.cs:57,61` still references `EntityFindTarget`, deleted this week with no replacement
   — this is also the class the CLAUDE.md "Enemy targeting (NEW-1)" checklist item already flagged
   as needing reimplementation; it is now not just incomplete, it is a hard compile error.

**Even once it compiles again**, source reading surfaced three further breaks that will fire the
moment an enemy dies or a ranged weapon is fired:

5. `EntityDeathState.cs:17` emits `ON_ENEMY_DEATH` with a `Vector3` position payload, but both
   subscribers — `EnemySpawner.ReleaseEnemy` and `ItemSpawner.DropItem` — cast the event payload to
   `GameObject`. This is an `InvalidCastException` (lỗi ép kiểu không hợp lệ) on every single enemy
   death, not an edge case.
6. `EnemySpawner.OnDisable()` calls `EventManager.Resgister` instead of `EventManager.UnResgister`
   for `ON_ENEMY_DEATH` — a copy-paste of the register call left in the unregister slot. This is a
   double-subscription bug (đăng ký sự kiện hai lần): every scene reload/disable-enable cycle adds a
   second live subscription, so `ReleaseEnemy`/spawn-count bookkeeping runs twice per death after the
   first reload.
7. `RangeWeapon.cs:7` declares `[SerializeField] private IObjecPoolService poolManager` — Unity
   cannot serialize an interface field through the Inspector, and unlike `EnemySpawner`/`ItemSpawner`
   there is no `[Inject] Construct(...)` DI wiring for it. `poolManager` will always be `null` at
   runtime, so ranged combat silently never fires a projectile — no exception, no log, just a dead
   weapon type.

**Severity**: S1 — blocks build entirely (items 1–4); items 5–7 are S1/S2 functional breaks that
will surface the instant compilation is restored.
**Priority**: P1 — must be the literal first commit of sprint-12. Nothing else in this report can be
verified against a running build until this lands.

## Systemic Trends

1. **Refactor discipline gap: deletions are landing without a reference sweep.** This is the second
   time in two weeks a deletion-based fix has left dangling call sites — `EntityStatsSO.cs` and
   `EntityWeaponMelee.cs` were deleted to fix BUG-042/043/046/NEW-2, but the callers (`EntityData`,
   `Entity.cs`, `EntityInput.cs`, `EntityAttack.cs`, `EntityEffectStats.cs`) were not updated in the
   same change. **Recommend**: no PR that deletes a public type/field/getter should be considered
   "fixed" until a full-solution `grep` for the deleted symbol returns zero hits. This should be a
   pre-commit or pre-push gate (S10-02's process-gate item — still open, 6+ cycles per the 08-22
   triage — this is exactly the class of bug it was designed to catch).
2. **CLAUDE.md is being updated optimistically, ahead of a green build.** The 2026-08-28 changelog
   marks 6 bugs "FIXED" based on the intent of the change, not a compile-verified state. Recommend
   the doc-update step in the fix workflow require "Unity Console shows zero errors" as a
   precondition, not just "the target line was changed as intended."
3. **`Vector3`/`GameObject` payload mismatch on `ON_ENEMY_DEATH` (BUG-064 item #5) is a second
   instance of a known event-bus foot-gun**: `EventManager.Emit` takes an untyped `object` payload
   (per `manager-event-code.md`, "pass typed data as the second argument — never pass raw `object`
   without casting" is already a written rule) and there is no compile-time check that emitter and
   subscribers agree on the payload type. Recommend a typed wrapper or at minimum an EditMode test
   per event that asserts payload type agreement across all registered handlers.
4. **`tests/EditMode/` and `tests/PlayMode/` are still empty (TD-014, unchanged for months).** Every
   one of this week's "claimed fixed" bugs (BUG-042/043/044/046/033) is a Logic or Integration story
   under `test-standards.md` and should be BLOCKING without an automated test. None has one. This is
   the direct cause of why six bugs could be marked "Done" in a doc while the build itself doesn't
   compile — there is no automated gate that would have caught it before a human (or this triage)
   read the diff by hand.
5. **Ranged combat (BUG-064 item #7) has been silently dead for at least one DI-related refactor
   cycle** without anyone noticing, because there's no smoke check that fires a ranged weapon.
   `/smoke-check` should include "equip ranged weapon, fire once, confirm projectile spawns" as a
   minimum scripted step, not just "does the scene load."
