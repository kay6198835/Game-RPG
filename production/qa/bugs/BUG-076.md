# BUG-076

**Title**: Ability cost is paid once per effect on top of the activation payment — a 3-effect ability charges its full `Costs` four times per cast
**Severity**: S2 (was S1 as filed — lowered 2026-09-22 after owner review; the balance-breaking half was fixed in `73ab8e7`)
**Priority**: 2
**System**: Abilities v2 / Core
**Found by**: Manual code review of the Abilities v2 architecture, 2026-09-21 (`origin/feature/fix-player-control`, HEAD `15242e6`)
**Status**: ✅ FIXED 2026-09-22 by `2a83469` — (a) by design, (b) withdrawn, (b′) and (c) both fixed. `AbilityDefinition.TryStart()` (`:50-64`) is now a single gate that checks every ability-scope cost against `IVitalComponent` generically over `StatType`, and the three condition walks collapsed to one. See the post-fetch re-verification at the end of this file. *Previous status line:* ⚠️ OPEN (S2), heavily re-scoped. Original double-charge FIXED by design change in `73ab8e7`. Owner review 2026-09-22 resolved two of the three replacement defects. Remaining: (b′) ability-scope `TryPayCost()` has no affordability gate — Avatar of Light’s 50 HP cost is unvalidated; (c) conditions walked 3× per activation.

## Description

`Assets/Script/System/Abilities/Core/AbilityInstance.cs`:

- `TryActivateInstant()` (line 41) validates conditions, then calls `TryPayCost()` — payment #1.
- `TryCastInstant()` (line 56) calls `Casting()`.
- `Casting()` (line 77) iterates `Definition.Effects`; for every effect whose `Casting(context)`
  returns `true` it calls `TryPayCost()` again.
- `TryPayCost()` (line 155) is not a per-effect partial charge: it loops the **entire**
  `Definition.Costs` list and calls `Owner.PayCost(...)` for each entry.

`AbilityEffectDefinition.Casting()` returns `true` by default whenever `SubConditions` are satisfied,
so an ability with three effects and a 15 Mana cost drains 15 × 4 = 60 Mana per activation.

For `AbilityActivationType.Hold` abilities the multiplier compounds further: `AbilityHolder.HandleInput()`
calls `TryCastInstant()` once per `AnimationOnAction` event while the ability sits in
`AbilityState.Cast`, so the charge repeats each time.

`TryPayCost()` also re-runs the full `Conditions` loop that `TryActivateInstant()` already ran through
`ValidateConditions()` — duplicate work with a different early-exit contract (a failed condition in
`TryPayCost` returns `false` *after* some `Owner.PayCost` calls may already have executed in a prior
iteration of `Casting()`).

## Reproduction

1. Author an `AbilityDefinition` with `Costs = [{ statType: Mana, value: 15 }]` and two or more effects.
2. Note the player's current Mana, cast the ability once.
3. Observe Mana drops by 45–60 instead of 15.

## Suggested Fix

Decide the intended contract first — there is no GDD for Abilities v2 (BUG-052):

- If cost is **per activation**: remove the `TryPayCost()` call from `Casting()` and keep only the one
  in `TryActivateInstant()`.
- If cost is **per channel tick** (Hold abilities draining a resource): move it out of the effect loop,
  scale it by `deltaTime`, and gate it on `ActivationType == Hold`.

Either way, split `TryPayCost()` into `ValidateConditions()` + `PayCost()` so payment and validation
are not interleaved.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**RE-SCOPED.** The defect as originally written — one cost list charged once at activation and then
again per effect — no longer exists. `73ab8e7` ("coding update flow ability, update logic cost")
changed the design rather than the arithmetic. Three different cost defects now occupy the same
code, so this ID is re-scoped rather than closed.

### What changed: two independent cost lists

| List | Declared | Charged at | Via |
|---|---|---|---|
| `AbilityDefinition.Costs` | `AbilityDefinition.cs:25` | once, on activation — `TryActivateInstant()` (`AbilityInstance.cs:42-56`) | `TryPayCost()` (`:164-178`) |
| `AbilityEffectDefinition.Costs` (**new** in `73ab8e7`) | `AbilityEffectDefinition.cs:9` | per effect, during `Casting()` (`AbilityInstance.cs:78-88`) | `TryPayEffectCost()` (`:155-162`) |

The two lists are disjoint. The original "same `Costs` charged N+1 times" is genuinely gone.

### New defect (a) — held abilities re-charge the per-effect cost every frame of the hold

`AbilityInstance.cs:57-65`:

```csharp
public void TryCastInstant()
{
    Casting();                                             // charges per-effect Costs
    if (Definition.ActivationType == AbilityActivationType.Hold)
    {
        if (IsHolding) return;                             // early-return KEEPS State == Cast
    }
    ChangeState(AbilityState.Do);
}
```

`Casting()` runs **before** the early return, and the early return leaves `State` at
`AbilityState.Cast`. `AbilityHolder.HandleInput()` (`:126-140`) dispatches on `State`, so every
subsequent `HandleInput()` while the button is held re-enters `TryCastInstant()` and charges
`effect.Costs` again. Cost is drained for the entire duration of the hold, once per dispatch.

Live today: Paladin **Blessed Slash** is authored as `AbilityActivationType.Hold`.

**Severity: S1.** Directly resource-breaking on a shipped ability.

### New defect (b) — `TryPayEffectCost()` never checks affordability

`AbilityInstance.cs:155-162`:

```csharp
private void TryPayEffectCost(List<StatCost> statCosts)
{
    if (statCosts.Count == 0) return;                      // no null guard either — see BUG-082
    foreach (var statCost in statCosts)
    {
        Owner.PayCost(statCost.statType, statCost.value);  // unconditional
    }
}
```

Despite the `Try` prefix it returns `void` and has no sufficiency test. `PayCost()`
(`AbilityHolder.cs:65-68`) forwards to `VitalStatsComponent.Reduction()`, which clamps at zero
(`VitalComponent.cs:49-60`). So casting without enough of a resource does not fail — it silently
drains the stat to `0` and proceeds.

`AbilityEffectDefinition.CheckPayCostValid()` (`:24-32`) *does* test affordability and is reached
from `Casting()` (`:20`), but its result only gates whether `TryPayEffectCost` is called at all
(`AbilityInstance.cs:83-86`) — it does not make the payment itself safe, and it carries its own
unreachable null guard (**BUG-082**).

**Severity: S2.**

### New defect (c) — conditions are evaluated three times per activation

For one activation of one ability, `Definition.Conditions` is walked three times:

| # | Site | Code |
|---|---|---|
| 1 | `AbilityHolder.cs:109-112` | `foreach (var condition in currentAbility.Definition.Conditions) if (!condition.IsMet(...)) return false;` inside `TryDoAbility()` |
| 2 | `AbilityInstance.cs:44` | `ValidateConditions(AbilityContext)` at the top of `TryActivateInstant()` |
| 3 | `AbilityInstance.cs:166-171` | the *same* loop again, inline at the top of `TryPayCost()` |

Evaluations 2 and 3 are two lines apart in the same call: `TryActivateInstant()` calls
`ValidateConditions()` at `:44` and then `TryPayCost()` at `:49`, which re-runs the identical loop.
Note also that evaluation 1 is unguarded against a null element, while 2 and 3 both skip nulls —
so a null entry in `Conditions` throws in `AbilityHolder` but not in `AbilityInstance`.

This is not merely wasteful: `HasEnoughManaCondition.IsMet()` **writes to serialized asset fields**
(**BUG-077**), so three evaluations means three asset writes per button press.

**Severity: S3** on its own; it is an amplifier for BUG-077.

### Still blocked on the same design decision

`AbilityEffectDefinition.Casting()`'s contract remains undefined — what it is for, whether it may
have side effects, and whether per-effect costs belong there at all. Until an ADR or the Abilities
v2 GDD settles it, defect (a) cannot be fixed without guessing. Same blocker as BUG-078 and
demo-checklist item 21.

## Owner review — 2026-09-22 — defects (a) and (b) resolved; only (c) stands

The three defects recorded in the re-verification section above were put to the owner. Two are
answered; one was not understood and is restated below in full.

### (a) Hold re-charges per-effect cost — **BY DESIGN, and dormant today**

**Owner's position:** this is the intended flow.

**Accepted.** `TryCastInstant()` (`AbilityInstance.cs:57-65`) running `Casting()` before the
`if (IsHolding) return;` early return is a channelled-cast model: a held ability keeps paying while
it is held. That is a legitimate design; it had simply never been written down, which is why the
review flagged it. Recording it here is the point.

**Additionally verified: it charges nothing today.** Every Paladin asset was checked for a
serialized `Costs` field:

```
Costs present?   asset
  yes            Avatar of Light                        (ability-scope)
  yes            Paladin Blessed Slash Ability          (ability-scope)
  yes            Blessing                               (ability-scope)
  yes            Consecrate                             (ability-scope)
  no             Gain For Time Effect
  no             Recovery Stat Effect
  no             Paladin Recovery Reduction Stats Effect   (x2)
  no             Paladin Spawn Slash Effect
  no             Paladin Buff - Debuff Stat Effect
  no             Paladin Spawn Consecrat Effect
```

**No effect asset carries a per-effect `Costs` list.** All seven predate the field added in
`73ab8e7`, so Unity materialises an empty list and `TryPayEffectCost()` returns immediately at
`statCosts.Count == 0`. Blessed Slash — the only `ActivationType: 1` (Hold) ability — pays its
5 Mana once from `AbilityDefinition.Costs` and nothing during the hold.

So the channelled-cost model is **designed but not yet exercised**. When a designer does fill in a
per-effect cost, the drain will be `cost × (number of HandleInput() dispatches during the hold)`,
which — ✏️ **corrected 2026-09-22** — is *not* frame-order dependent: `AbilityHolder.HandleInput()` is driven by `PlayerSkillWeaponState.AnimationOnAction()` (`:47`), a Unity Animation Event (`Player.cs:78`), so the rate follows the hold animation’s length and is frame-rate independent. The open question is sustain-vs-purchase semantics, not frame timing. Worth a tuning note in the Abilities v2 GDD;
not a bug.

### (b) `TryPayEffectCost` does not check affordability — **CORRECTED, mostly wrong**

**Owner's position:** the check already happens in the base class before payment; `Casting()` will
be renamed `TryCasting()` to make that explicit. If it passes, resources are sufficient.

**Verified, and the owner is right for the effect-scope path.** The gate is real:

```csharp
// AbilityEffectDefinition.cs:11-22
public virtual bool Casting(AbilityContext context)
{
    ... SubConditions ...
    if (!CheckPayCostValid(context)) return false;     // :20 — affordability gate
    return true;
}

// :24-32
protected virtual bool CheckPayCostValid(AbilityContext context)
{
    ...
    if (cost.value > context.Services.Vital.GetCurrentStatValue(cost.statType)) return false;
}

// AbilityInstance.cs:83-86 — payment happens ONLY inside the gate
if (effect.Casting(AbilityContext))
{
    TryPayEffectCost(effect.Costs);
}
```

The original finding — "an unaffordable cast silently drains the stat to zero" — is **withdrawn for
the effect-scope list.** The rename to `TryCasting()` is the right call: a method named `Casting()`
returning `bool` does not read as a gate, which is exactly why the review misread it.

**What survives, and it is a different code path.** The **ability-scope** list has no affordability
check at all:

```csharp
// AbilityInstance.cs:164-178
private bool TryPayCost()
{
    foreach (var condition in Definition.Conditions)        // conditions only
    {
        if (!condition.IsMet(AbilityContext)) return false;
    }
    foreach (var statCost in Definition.Costs)
    {
        Owner.PayCost(statCost.statType, statCost.value);   // unconditional
    }
    return true;
}
```

No `CheckPayCostValid` equivalent here. The only thing standing in for it is
`HasEnoughManaCondition`, which checks **`StatType.Mana` and nothing else**.

Confirmed against the asset — `Avatar of Light.asset`:

```yaml
Costs:
- value: 40
  statType: 101      # Mana  — checked by HasEnoughManaCondition
- value: 50
  statType: 100      # HP    — checked by NOTHING
```

`PayCost()` → `VitalStatsComponent.Reduction()` clamps at `0` (`VitalComponent.cs:49-60`), so casting
Avatar of Light below 50 HP drains the player to exactly 0 HP, does not kill them, and reports
nothing. **This half stands** and is a live gameplay bug on a shipped ability.

Cleanest fix, given the owner's direction on naming: lift the same pattern up one level — a
`CheckPayCostValid(Definition.Costs)` gate at the top of `TryPayCost()`, generic over `StatType`.
That also makes `HasEnoughManaCondition` redundant and closes BUG-077 in the same motion.

### (c) Conditions evaluated three times per activation — **restated**

One press of the ability button walks `Definition.Conditions` **three separate times**. Not three
conditions — the *same list*, three times.

Full call chain for one activation:

```
PlayerInputHandle.OnSkillWeapon()  :254
  └─ AbilityHolder.TryDoAbility(AbilitySlot.Utility)
       :107  currentAbility.CanStart()
       :108  currentAbility.SetupContext()
       :109  foreach (var condition in currentAbility.Definition.Conditions)   ◄── WALK 1
       :111      if (!condition.IsMet(currentAbility.AbilityContext)) return false;

   ... animation event fires ...

AbilityHolder.HandleInput()  :128  case AbilityState.Start:
  └─ AbilityInstance.TryActivateInstant()  :42
       :44   if (!ValidateConditions(AbilityContext)) return false;
               └─ :143  for (i = 0; i < Definition.Conditions.Count; i++)      ◄── WALK 2
                  :148      if (!condition.IsMet(context)) return false;

       :49   if (!TryPayCost()) return false;
               └─ :166  foreach (var condition in Definition.Conditions)       ◄── WALK 3
                  :169      if (!condition.IsMet(AbilityContext)) return false;
                  :173  foreach (var statCost in Definition.Costs) PayCost(...)
```

**Walks 2 and 3 are five lines apart, inside the same method call.** `TryActivateInstant()` calls
`ValidateConditions()` at `:44`, then calls `TryPayCost()` at `:49`, and the first thing
`TryPayCost()` does is run the identical loop again. Walk 3 is a verbatim duplicate of walk 2, with
nothing changed in between that could alter the result.

**Why it is not merely wasteful.** `HasEnoughManaCondition.IsMet()` (`:11-12`) **writes to two
serialized `ScriptableObject` fields** every time it runs:

```csharp
currentMana = context.Services.Vital.GetCurrentStatValue(StatType.Mana);
costMana    = context.AbilityDefinition.GetCostValues(StatType.Mana);
```

Those are asset-level fields, so each write marks
`Assets/SO/Skill/Conditions/Has Enough Mana Condition.asset` dirty and Unity saves it. That asset is
**shared by all four Paladin abilities** (GUID `02cbacd1d0342774abb852a2ed63f9b4`). So:

> **3 walks × 1 write each = three writes to a committed `.asset` file, per button press.**

Those writes reach git as modified-asset noise — the same class of incident as BUG-063, which
required a manual asset cleanup on `sprint-10`.

There is also an inconsistency between the walks: walk 1 (`AbilityHolder.cs:109-112`) has **no null
guard** on the list element, while walks 2 and 3 both do `if (condition == null) continue`. A null
entry in `Conditions` therefore throws in `AbilityHolder` but is skipped in `AbilityInstance`.

**Fix:** delete walk 3 (`AbilityInstance.cs:166-171`) — it is a pure duplicate of walk 2 and removing
it changes no behaviour. Then decide whether walk 1 is needed at all, given that
`TryActivateInstant()` re-validates: if the intent is "fail fast before playing the animation", keep
it and add the null guard; if not, remove it and leave `ValidateConditions()` as the single
evaluation point. Fixing BUG-077 (a) independently removes the asset-write consequence, but the
duplicate walk should go regardless.

## Re-verification — 2026-09-22 (post-fetch, HEAD `2a83469`) — **FIXED, closing**

Commit `2a83469` ("coding") landed the owner's stated plan from the review above, and it resolves
both remaining sub-items.

### (b′) — ability-scope costs now have an affordability gate, generic over `StatType`

`AbilityDefinition.cs:50-64`, new:

```csharp
public virtual bool TryStart(AbilityContext abilityContext)
{
    if ((Conditions == null || Conditions.Count == 0) &&
        (Costs == null || Costs.Count == 0)) return true;
    foreach (var condition in Conditions)
    {
        if (!condition.IsMet(abilityContext)) return false;
    }
    foreach (var cost in Costs)
    {
        if (cost.value > abilityContext.Services.Vital.GetCurrentStatValue(cost.statType))
            return false;                                     // ← the gate (b′) asked for
    }
    return true;
}
```

Called from `AbilityInstance.CanStart():94`, which `AbilityHolder.TryDoAbility():107` calls before
any state change. `TryPayCost()` — which paid unconditionally — is **deleted**; payment is now
`PayCost(Definition.Costs)` inside `ActivateInstant():44`, reached only after `CanStart()` passed.

This reads the cost's own `statType` through `IVitalComponent`, so it covers every stat, not just
Mana. The live case this bug was filed on:

```yaml
# Avatar of Light.asset
Costs:
- {value: 40, statType: 101}   # Mana — was checked by HasEnoughManaCondition
- {value: 50, statType: 100}   # HP   — was checked by nothing; now checked here
```

Casting Avatar of Light below 50 HP is now refused at `CanStart()` instead of draining the player to
exactly 0 HP without dying.

### (c) — three condition walks collapsed to one

| Walk (as filed) | Site at `d17fcc5` | State at `2a83469` |
|---|---|---|
| 1 | `AbilityHolder.cs:109-112` | **deleted** (`TryDoAbility()` is now `CanStart()` + animator assignment only) |
| 2 | `AbilityInstance.ValidateConditions()` | **method deleted** |
| 3 | `AbilityInstance.TryPayCost():166-171` | **method deleted** |
| — | — | **one** walk remains: `AbilityDefinition.TryStart():56-59` |

`grep -rn "IsMet(" Assets/Script --include=*.cs` now returns a single call site. The "three asset
writes per button press" consequence is doubly gone: the condition class that did the writing was
deleted in the same commit (**BUG-077**).

### (a) and (b) — unchanged from the owner review above

(a) channelled per-effect cost on `Hold` remains **by design** and still dormant (no effect `.asset`
carries a `Costs` list). (b) remains **withdrawn**; `Casting()` was renamed to `TryCast()` in this

**Status: Open (S2) → FIXED.** All four sub-items are resolved: (a) by design, (b) withdrawn,
(b′) fixed, (c) fixed.
