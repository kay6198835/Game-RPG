# BUG-077

**Title**: `HasEnoughManaCondition` writes runtime values into serialized `ScriptableObject` fields — same data-corruption class as BUG-063
**Severity**: S1 (active data-corruption risk on a committed `.asset` file)
**Priority**: 1
**System**: Abilities v2 / Conditions
**Found by**: Manual code review of the Abilities v2 architecture, 2026-09-21 (`origin/feature/fix-player-control`, HEAD `15242e6`)
**Status**: Open

## Description

`Assets/Script/System/Abilities/Conditions/HasEnoughManaCondition.cs:6-7`:

```csharp
public float currentMana;
public float costMana;
```

Both are `public` on a `ScriptableObject`, so Unity serializes them. `IsMet(context)` (line 9) assigns
to both on every call — and `IsMet` runs from three separate paths per activation
(`AbilityHolder.TryDoAbility()`, `AbilityInstance.ValidateConditions()`, `AbilityInstance.TryPayCost()`).

In the Editor this marks the asset dirty and the live Mana reading gets written into
`Assets/SO/Skill/Conditions/Has Enough Mana Condition.asset`, which is committed. That is exactly the
failure mode `.claude/rules/scriptableobject-data.md` was amended to forbid after BUG-063
("Do not add `[SerializeField]` to a field holding runtime state, under any preprocessor guard") —
here the field does not even need a `[SerializeField]`, `public` is enough.

The two fields are debug-inspection only; nothing reads them. The condition body recomputes both
values inline on the next two lines and ignores the cached copies.

## Suggested Fix

Delete both fields:

```csharp
public override bool IsMet(AbilityContext context)
{
    float current = context.Services.Vital.GetCurrentStatValue(StatType.Mana);
    float cost = context.AbilityDefinition.GetCostValues(StatType.Mana);
    return current >= cost;
}
```

If the values are wanted for debugging, make them `[System.NonSerialized] public` or expose them
through a read-only property computed on demand. Then revert any runtime values already committed into
`Has Enough Mana Condition.asset`.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Still open, unchanged in source. Four additions, and the asset-level blast radius is considerably
wider than this file recorded.**

The whole class, for reference —
`Assets/Script/System/Abilities/Conditions/HasEnoughManaCondition.cs`:

```csharp
 4: public class HasEnoughManaCondition : AbilityConditionDefinition
 6:     public float currentMana;
 7:     public float costMana;
 9:     public override bool IsMet(AbilityContext context)
11:         currentMana = context.Services.Vital.GetCurrentStatValue(StatType.Mana);
12:         costMana = context.AbilityDefinition.GetCostValues(StatType.Mana);
13:         if (context.Services.Vital.GetCurrentStatValue(StatType.Mana)
14:          < context.AbilityDefinition.GetCostValues(StatType.Mana))
15:             return false;
16:         return true;
```

### (a) The two fields are pure garbage — nothing reads them

`:11-12` write `currentMana` and `costMana`. `:13-14` then **recompute both values from scratch**
for the comparison rather than using the fields just assigned. Neither field is read anywhere in
this class or anywhere else in the project. They exist only to be written. Deleting both lines
changes no behaviour.

### (b) They are asset-level fields, so the write reaches git

`AbilityConditionDefinition` is a `ScriptableObject`. `public float` on a `ScriptableObject` is a
serialized field. Unity marks the asset dirty when a serialized field changes in the Editor, and
saves it — so every playtest writes live mana values into

`Assets/SO/Skill/Conditions/Has Enough Mana Condition.asset`

which is committed. This is the same defect class as **BUG-063** and a direct violation of
`.claude/rules/scriptableobject-data.md` ("Do not add `[SerializeField]` to a field holding runtime
state, under any preprocessor guard"). Unlike BUG-063 it needs no preprocessor argument — the fields
are `public`, so they serialize in every configuration.

### (c) One shared asset, four abilities, three writes per cast

The condition asset is not per-ability. GUID `02cbacd1d0342774abb852a2ed63f9b4` is referenced by:

```
Assets/SO/Skill/Paladin/Ability/Avatar of Light/Avatar of Light.asset
Assets/SO/Skill/Paladin/Ability/Blessed Slash/Paladin Blessed Slash Ability.asset
Assets/SO/Skill/Paladin/Ability/Blessing/Blessing.asset
Assets/SO/Skill/Paladin/Ability/Consecrate/Consecrate.asset
Assets/SO/Skill/ShootSpirit/MainEffect/ShootSpirit.asset
Assets/SO/Skill/ShootSpirit/SpiritBomd.asset
```

All four live Paladin abilities plus the two broken ShootSpirit assets. They write over each other
in the same file, so the committed values are whichever ability cast last.

Worse: per **BUG-076 defect (c)**, `Definition.Conditions` is evaluated **three times per
activation** (`AbilityHolder.cs:109-112`, `AbilityInstance.cs:44`, `AbilityInstance.cs:166-171`).
That is three asset writes per button press.

### (d) It only checks Mana — HP costs are unchecked, and that is a live gameplay bug

`IsMet()` hardcodes `StatType.Mana`. `Avatar of Light` is authored with a cost of **40 Mana + 50
HP**. The HP half is validated by nothing:

- this condition does not look at it;
- `AbilityInstance.TryPayCost()` (`:164-178`) pays unconditionally after conditions pass;
- `AbilityHolder.PayCost()` (`:65-68`) forwards to `VitalStatsComponent.Reduction()`, which clamps
  at zero (`VitalComponent.cs:49-60`).

So casting Avatar of Light at low HP drains the player to exactly `0` HP, does not kill them
(nothing transitions to `PlayerDeathState` from a cost payment), and reports nothing. That is a
gameplay defect in its own right, not just a validation gap.

### (e) Duplicated by a newer, generic mechanism

`73ab8e7` added `AbilityEffectDefinition.CheckPayCostValid()` (`:24-32`), which walks the generic
`Costs` list and compares each against `Services.Vital.GetCurrentStatValue(cost.statType)` — exactly
what this condition does, but for every stat rather than hardcoded Mana, and at effect scope rather
than ability scope. Two parallel affordability mechanisms now coexist, checking different lists at
different times.

### Suggested fix (revised)

1. Delete `currentMana` and `costMana` (`:6-7`) and the two assignments (`:11-12`). One-line
   behaviour-preserving cleanup that closes the data-corruption half immediately.
2. Then decide — with the same ADR/GDD that settles `Casting()`'s contract — whether
   `HasEnoughManaCondition` should exist at all, or whether `CheckPayCostValid()` should be promoted
   to ability scope and the condition deleted. Point (d) argues for the generic mechanism: a
   hardcoded per-stat condition cannot cover multi-stat costs.
3. Step 1 does not depend on step 2. Do it now.
