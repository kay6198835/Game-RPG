# BUG-078

**Title**: `SpawnSummonEffect.Casting()` returns its gate inverted and spawns the summon a second time in `Apply()`
**Severity**: S1 as filed — **downgraded to non-issue 2026-09-22.** One half was a real bug (fixed); the other half was a misreading of an intentional two-object effect
**Priority**: 2
**System**: Abilities v2 / Spawn effects
**Found by**: Manual code review of the Abilities v2 architecture, 2026-09-21 (`origin/feature/fix-player-control`, HEAD `15242e6`)
**Status**: ✅ CLOSED 2026-09-22 — inverted return FIXED in `73ab8e7`; double spawn confirmed BY DESIGN by owner review and verified against the Consecrate asset (RuneCircle telegraph + Lightning payload). No code change required.

## Description

`Assets/Script/System/Abilities/Effects/SpawnSummonEffect.cs:20-25`:

```csharp
public override bool Casting(AbilityContext context)
{
    if (!base.Casting(context)) return true;
    base.Apply(context);
    return false;
}
```

Two problems:

1. **Inverted return.** `AbilityInstance.Casting()` treats a `true` return as "this effect fired, charge
   the cost" (see BUG-076). Here the *failure* branch — `base.Casting(context)` false, i.e. a
   `SubCondition` was not met — returns `true`, and the *success* branch returns `false`. So the cost is
   charged precisely when the effect did **not** run, and skipped when it did.

2. **Double spawn.** `Casting()` calls `base.Apply(context)` (the `SpawnEffectBase` projectile-style
   spawn, using `SpawnPos()`/`Angle()`), and then `AbilityInstance.TryDoInstant()` → `Execute()` calls
   the overridden `Apply(context)` (line 14), which spawns `summonPrefab` again through
   `context.Services.Pool.Spawn(...)`. A single Consecrate cast therefore instantiates two pooled
   objects, only one of which ever gets its `Launch(...)` callback wired the way `SummonExecute`
   expects.

   The two spawns are not even the same prefab: `base.Apply` spawns `SpawnEffectBase.Prefab`,
   the override spawns `SpawnSummonEffect.summonPrefab`.

Also in the override `Apply()` (line 16-18): `obj.GetComponent<SpawnSummonBase>()` is dereferenced with
no null check, unlike `base.Apply()` which guards and logs.

## Reproduction

1. Cast Paladin Consecrate in `LoadRandomMap`.
2. Observe two spawned objects (rune circle + lightning prefab) where one is expected.
3. Give the ability a `SubCondition` that fails; observe the Mana cost is still deducted.

## Suggested Fix

Settle what `Casting()` is for first (BUG-076 blocks this — the contract is undefined). Assuming
"return true when this effect consumed the cast":

```csharp
public override bool Casting(AbilityContext context)
{
    if (!base.Casting(context)) return false;
    Apply(context);
    return true;
}

public override void Apply(AbilityContext context)
{
    if (summonPrefab == null) return;
    var obj = context.Services.Pool.Spawn(summonPrefab.gameObject, context.TargetPoint, Quaternion.identity);
    if (obj.TryGetComponent<SpawnSummonBase>(out var controller))
        controller.Launch(Lifetime, context, SummonExecute);
}
```

and make sure `AbilityInstance` does not also call `Apply()` for an effect that already ran in `Casting()`.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**This bug was filed as one defect; it is two. One is fixed, one is not.**

### Half A — inverted `Casting()` return: **FIXED** in `73ab8e7`

`Assets/Script/System/Abilities/Effects/SpawnSummonEffect.cs:20-25` now reads:

```csharp
public override bool Casting(AbilityContext context)
{
    if (!base.Casting(context)) return false;
    base.Apply(context);
    return true;
}
```

The gate polarity is correct: a failing `base.Casting()` short-circuits, so the cost is no longer
charged on the failure path.

### Half B — double spawn: **STILL OPEN**

`Casting()` and `Apply()` are both called on every effect in `Definition.Effects` during one
ordinary cast, at two different `AbilityState` phases:

| Phase | Call chain | Site |
|---|---|---|
| `Cast` | `AbilityHolder.HandleInput()` → `AbilityInstance.TryCastInstant()` (`:57`) → `Casting()` (`:59`) → `AbilityInstance.Casting()` (`:78-88`) → `effect.Casting(AbilityContext)` (`:83`) | `AbilityInstance.cs` |
| `Do` | `AbilityHolder.HandleInput()` → `AbilityInstance.TryDoInstant()` (`:66`) → `Execute()` (`:68`) → `AbilityInstance.Execute()` (`:180-190`) → `effect.Apply(context)` (`:188`) | `AbilityInstance.cs` |

`SpawnSummonEffect` spawns in both, from **two different prefab fields**:

| Path | Line | Prefab field | Callback |
|---|---|---|---|
| `Casting()` → `base.Apply()` | `SpawnEffectBase.cs:10-31`, spawn at `:25` | `Prefab` (inherited, `SpawnEffectBase.cs:5`) | `Execute` — and `SpawnSummonEffect.Execute()` (`:28-31`) is `//Do nothing` |
| `Apply()` | `SpawnSummonEffect.cs:14-19`, spawn at `:16` | `summonPrefab` (`:7`) | `SummonExecute` (`:33-41`) — the one that actually deals damage |

Three outcomes depending on how the asset is filled in the Inspector:

1. **Both fields point at the same asset** → two identical summon objects spawn per cast; only one
   of them can ever deal damage.
2. **Only `summonPrefab` is assigned** → `base.Apply()` early-returns at `SpawnEffectBase.cs:12-16`
   and logs `Debug.LogWarning("[ShootSpiritOrbEffect] OrbPrefab chưa được assign.")` on **every
   cast**. (The log prefix is also a dead class name — see BUG-073.)
3. **The two fields point at different assets** → two different objects spawn per cast.

### Hidden coupling — read this before "simplifying" the fix

`SpawnSummonEffect.Apply()` (`:14-19`) never assigns `_context`. But `SpawnPos()` (`:43-46`) reads
`_context.TargetPoint`, and `Angle()` (`:10-13`) is the only other override. The class works today
**only because `Casting()` runs first and `base.Apply()` sets `_context` at `SpawnEffectBase.cs:17`
on its behalf.**

Removing `base.Apply(context)` from `Casting()` — the obvious one-line fix for the double spawn —
will therefore produce a `NullReferenceException` in `SpawnPos()` unless `Apply()` is changed to set
`_context` itself. Anyone fixing this must do both edits together.

This is an instance of the shared-mutable-state-on-a-ScriptableObject problem: `_context` and `dir`
are fields on `SpawnEffectBase` (`:8-9`), which is a single shared asset instance.

### Blocked on a design decision

Which of `Casting()` and `Apply()` is supposed to spawn cannot be decided from code, because
`AbilityEffectDefinition.Casting()` has no defined contract. That is the same blocker recorded for
BUG-076 and in demo-checklist item 21 of `CLAUDE.md`: **a GDD for Abilities v2 is the real
prerequisite.**

## Owner review — 2026-09-22 — CLOSED, BY DESIGN. Finding retracted.

**Owner's position:** the double spawn is intentional — the effect deliberately controls **two
objects within one effect**.

**Verified against the live asset, and the owner is right. This is not a defect.**

`Assets/SO/Skill/Paladin/Ability/Consecrate/Effect/Paladin Spawn Consecrat Effect.asset`:

```yaml
m_Script: {guid: e3551c5d68af9dd4dbd570c6d2682e46}   # SpawnSummonEffect
m_Name: Paladin Spawn Consecrat Effect
Prefab:       {guid: d34555be92d2a04429095bfd23e184a9}   # Assets/Prefab/Particle Effect/RuneCircle.prefab
summonPrefab: {guid: f61a428b3c1e2da408aae132570cb765}   # Assets/Prefab/Particle Effect/Lightning.prefab
baseDamage: 30
```

The two prefab fields are **two different objects with two different jobs**, spawned at two
different phases of the same cast:

| Phase | Field | Prefab | Callback | Role |
|---|---|---|---|---|
| `Cast` — `Casting()` → `base.Apply()` | `Prefab` | `RuneCircle.prefab` | `Execute()` = `//Do nothing` | **Telegraph.** A ground marker shown while the cast is charging. Deals no damage, so a no-op callback is correct, not an oversight |
| `Do` — `Apply()` | `summonPrefab` | `Lightning.prefab` | `SummonExecute` | **Payload.** The strike, fired from a Unity Animation Event on the lightning clip |

This is the standard telegraph-then-strike shape for a ground-targeted ability, and
`RuneCircleController` being an empty `SpawnSummonBase` subclass is consistent: it never needs to
override `Execute()` because it has no payload to deliver.

**What this retracts:**

- "Double spawn" is not a bug. Two objects per cast is the point.
- The three "outcomes depending on Inspector fill-in" listed in the re-verification section above
  are misread. Scenario 3 ("two different assets") is the *intended* configuration, not a failure
  mode. Scenario 2 (only `summonPrefab` assigned) remains a genuine authoring mistake that logs a
  warning every cast, but that is an asset-validation concern, not a code defect.
- The "hidden coupling" note stands as a **fact** but not as a criticism: `Apply()` relies on
  `Casting()` having set `_context`, which is correct given that `Casting()` always runs first in
  the `Cast → Do` sequence. It is worth a code comment so a future reader does not "fix" it, but it
  is not a defect to file.

**Status of this bug overall:**

| Half | Verdict |
|---|---|
| Inverted `Casting()` return | ✅ **FIXED** in `73ab8e7` — `SpawnSummonEffect.cs:20-25` short-circuits correctly |
| Double spawn | ✅ **BY DESIGN** — confirmed against the Consecrate asset, 2026-09-22 |

**BUG-078 is closed.** No code change required.

**Follow-up worth having (not filed as a bug):** add a `[Tooltip]` or `[Header]` on
`SpawnEffectBase.Prefab` and `SpawnSummonEffect.summonPrefab` naming their roles ("cast-phase
telegraph" / "do-phase payload"). The two fields are indistinguishable in the Inspector today, which
is what made this read as a duplicate.
