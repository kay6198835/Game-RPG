# BUG-053

**Title**: `EntityNegativeReciver.TakeDamage()` now contains player-only logic — fetches `PlayerInputHandler` and emits `ON_PLAYER_DEATH` from an enemy component
**Severity**: S1 (would throw/misbehave at runtime on the first enemy hit that reaches this path)
**System**: Enemy AI / Damage Chain
**Found by**: 2026-08-06 daily-standup (autonomous), while re-verifying BUG-042 after `c5f26b1` (merge of `origin/feature/enemy-control` into `sprint-08`)
**Status**: FIXED (verified 2026-09-06, `pm-weekly-wrapup` code-review pass, `sprint-12` HEAD `f3f5f08`)

## Update 2026-09-06

`Assets/Script/Character/Entity/CoreComponent/EntityNegativeReciver.cs` was rewritten (part of the
Sprint 12 entity/stat refactor merged via `feature/fix-player-control`). Current body no longer
resolves `PlayerInputHandler` off `EntityCore` and no longer emits `ON_PLAYER_DEATH`. It now reads:

```csharp
public class EntityNegativeReciver : EntityCoreComponent<EntityCore>, INegativeReceiver
{
    private EntityVitalStats entityVitalStats;
    private EntityStatsHandler entityStatsHandler;
    private EntityUIController entityUIController;
    private EntityInput entityInput;
    protected override void Start() { ... Core.GetCoreComponent(out entityVitalStats); ... }
    public void TakeDamage(float amoutDamage, Vector2 attackPosition)
    {
        float finalDamage = DamageCalculate(amoutDamage);
        if (finalDamage <= 0) return;
        entityVitalStats.ReceiveReduction(StatType.HP, finalDamage);
        entityInput.OnTakeDamage(attackPosition);
        entityUIController.UpdateUIHealth(UpdateUIHealth());
    }
    ...
}
```

Damage now routes through `EntityVitalStats`/`EntityStatsHandler` (the `Stats` SO path), matching
S8-02's original acceptance criteria in substance (one `INegativeReceiver` implementer on the enemy,
no player-only logic). Note the `TakeDamage` signature changed from `int` to `float amoutDamage` —
matches `INegativeReciver.cs`'s interface, no mismatch found.

**Caveat**: fixed in source only — no Play Mode / Editor session has confirmed this against a running
build at any point in Sprint 11 or Sprint 12 (see `BUG-064` for the compile-break history this was
entangled with). Recommend closing this file once an owner-in-Editor smoke pass confirms an enemy
takes damage and dies with no NRE.

## Original Description (2026-08-06, superseded)

`Assets/Script/Character/Entity/CoreComponent/EntityNegativeReciver.cs` was touched by tonight's
merge commit `c5f26b1` (`b74a14f` "update flow equid weapon, need check flow change attack statae").
It now reads:

```csharp
public class EntityNegativeReciver : EntityCoreComponent<EntityCore>, INegativeReceiver
{
    public int currentHealth;
    public void TakeDamage(int amoutDamage, Vector2 attackPosition)
    {
        if (currentHealth <= 0) return;
        currentHealth -= amoutDamage;
        Core.GetCoreComponent(out PlayerInputHandler input);
        input.OnTakeDamage(attackPosition);
        if (currentHealth <= 0)
            EventManager.Emit(EventID.ON_PLAYER_DEATH);
    }
}
```

This is an **Entity** (enemy) core component (`EntityCoreComponent<EntityCore>`), but the body was
copy-pasted from the player's `NegativeReciver` pattern:

- `Core.GetCoreComponent(out PlayerInputHandler input)` — `Core` here is `EntityCore`, which has no
  `PlayerInputHandler` sibling. This will either fail to resolve (`input` null) and NullRef on the next
  line, or silently do nothing depending on `GetCoreComponent`'s null-handling.
- `EventManager.Emit(EventID.ON_PLAYER_DEATH)` — fires the **player** death event when an **enemy**
  dies. Any listener wired to `ON_PLAYER_DEATH` (death UI, `PlayerData.Reborn()`, scene reload) would
  fire incorrectly on enemy kill.

This is a second, independent problem from BUG-042 (`EntityCore.TakeDamage()` still throws
`NotImplementedException`) and from BUG-043 (two divergent enemy attack paths) — it's the same
"duplicate `INegativeReceiver` implementer on the enemy" issue BUG-042's acceptance criteria calls out
("exactly one `INegativeReceiver` implementer on the enemy prefab"), except the duplicate is now filled
with actively wrong logic instead of being an inert stub.

## Impact

- If `EntityNegativeReciver` is the component that actually ends up on the enemy prefab (rather than
  `EntityCore` itself), the first successful hit on an enemy will either NullRef or wrongly trigger
  player-death handling.
- Blocks S8-02 acceptance criteria as written — cannot close BUG-042 by fixing `EntityCore.TakeDamage()`
  alone; this file needs to be reconciled (deleted or rewritten) in the same pass, exactly as
  `sprint-08.md` already anticipated ("delete or finish the duplicate `EntityNegativeReciver.cs` — do
  not leave both").

## Suggested Fix

Per S8-02's existing acceptance criteria: pick one `INegativeReceiver` implementer for the enemy
(recommend `EntityCore.TakeDamage()`, since `EntityCore` is the component hub per `engine-code.md`),
implement it for real (health decrement + `ON_ENEMY_DEATH`/death-state hookup), and delete
`EntityNegativeReciver.cs` entirely rather than fixing its player-copied body in place.
