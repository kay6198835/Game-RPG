# BUG-068

**Title**: `AbilityHolder.GetAbility()` dereferences `currentAbility.Definition` with no null check — NRE on any unbound `AbilitySlot`
**Severity**: S3 (downgraded from S1 by Sprint 14 triage and re-confirmed 2026-09-22 — `GetAbility()` has zero callers project-wide, so the defect is unreachable dead code)
**System**: Abilities v2 / Player
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-09-13 (autonomous, `lead-programmer` agent via `/code-review`)
**Status**: Open

## Description

`Assets/Script/Character/Player/CoreComponent/AbilityHolder.cs:83-89`:

```csharp
_equipped.TryGetValue(slot, out var instance);
...
currentAbility.Definition.AnimatorOverride   // no null check on instance / currentAbility
```

`_equipped.TryGetValue` returns `false` (with `instance` left `default`/`null`) when `slot` was never
bound via `abilityBindings` — a realistic authoring mistake, not a hypothetical, since
`AbilitySlot` (Primary/Secondary/Utility/Ultimate) has four values and nothing enforces all four
being bound in the Inspector. `PlayerInputHandler.OnSkillWeapon()`
(`Assets/Script/Character/Player/CoreComponent/PlayerInputHandle.cs:244-249`) calls into this path
on every skill input. This is the exact gap flagged as outstanding, but not yet fixed, in
`.claude/rules/prototype-code.md`'s Promotion Log for the Abilities v2 promotion (`9b8d40f`,
`5c7afba`).

## Impact

- First skill press on an unbound or misconfigured `AbilitySlot` throws `NullReferenceException`
  instead of failing gracefully (e.g., no-op).
- Blocks the sprint-13 goal of a clean-console Play Mode smoke session (S13-02) if any slot is left
  unbound on the Player prefab used for that session.

## Suggested Fix

Guard `GetAbility()` (and any other `_equipped.TryGetValue` call site) with the `bool` return value
from `TryGetValue` and return `null`/no-op when the slot isn't bound, instead of unconditionally
dereferencing `instance.Definition`. Log a named warning (`"AbilityHolder: no ability bound to slot
{slot}"`) rather than letting the NRE surface unlabelled.

## Status Update — 2026-09-19 (`pm-weekly-wrapup`)

Still open in code (`AbilityHolder.cs:93-99`) but **now dormant**: `GetAbility()` has **zero callers**
project-wide (`PlayerInputHandler.OnSkillWeapon` was rewritten to use `TryDoAbility`, which uses

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Still open, unchanged. Context added; the S1→S3 downgrade recorded in sprint-14 is confirmed
correct.**

### The defect

`Assets/Script/Character/Player/CoreComponent/AbilityHolder.cs:93-99`

```csharp
public AbilityInstance GetAbility(AbilitySlot slot)
{
    _equipped.TryGetValue(slot, out var instance);            // return value discarded
    currentAbility = instance;
    core.Player.Anim.runtimeAnimatorController = currentAbility.Definition.AnimatorOverride;   // :97
    return instance;
}
```

`TryGetValue`'s `bool` is dropped; on a miss `instance` is `null` and `:97` throws
`NullReferenceException` on any unbound `AbilitySlot`.

### Why it is S3, not S1 — zero callers

```
$ grep -rn "GetAbility(" Assets --include=*.cs
Assets/Script/Character/Player/CoreComponent/AbilityHolder.cs:93:    public AbilityInstance GetAbility(AbilitySlot slot)
```

One hit: the declaration. Nothing in the project calls it. It is dead code carrying a live defect —
unreachable today, and a trap for whoever wires up slot switching. The correct sibling pattern is
right below it: `TryDoAbility()` (`:100-116`) checks the `TryGetValue` result and returns `false` on
a miss.

### Second unguarded dereference in the same class

`AbilityHolder.cs:21-22`

```csharp
21:    public AbilityState CurrentAbilityState => currentAbility?.State ?? AbilityState.Start;
22:    public AbilityActivationType CurrentActivationType => currentAbility.Definition.ActivationType;
```

Line 21 uses the null-conditional; line 22, written beside it, does not — neither on
`currentAbility` nor on `.Definition`.

`CurrentActivationType` has exactly one caller, `PlayerInputHandle.cs:258`, and that call sits
inside the `if (abilityHolder.TryDoAbility(AbilitySlot.Utility)) { ... }` branch. `TryDoAbility()`
assigns `currentAbility` at `:106` before returning `true`, so the property is non-null **by
accident of call ordering, not by design**. Any second caller added outside that branch throws.

### Suggested fix (unchanged in shape, widened)

Guard both, matching `TryDoAbility()`:

```csharp
public AbilityInstance GetAbility(AbilitySlot slot)
{
    if (!_equipped.TryGetValue(slot, out var instance)) return null;
    currentAbility = instance;
    core.Player.Anim.runtimeAnimatorController = instance.Definition.AnimatorOverride;
    return instance;
}

public AbilityActivationType CurrentActivationType =>
    currentAbility?.Definition?.ActivationType ?? AbilityActivationType.Active;
```

Or delete `GetAbility()` outright — nothing uses it, and `TryDoAbility()` already covers the
lookup-and-select job correctly.
