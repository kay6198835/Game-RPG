**Severity**: S3 (latent today — masked by Unity's serializer and by all four ability assets having `Conditions: []`)
**Priority**: 3
**System**: Abilities v2 / Core
**Found by**: Post-fetch source re-verification, 2026-09-22 (branch `origin/feature/fix-player-control`, HEAD `2a83469`)
**Status**: ✅ FIXED 2026-09-22 (owner, working tree, uncommitted) — 4 of 6 items fixed, the other 2 made unreachable by `Costs = new()` on `:25`. Null-element guards added, `CheckPayCostValid()` deleted, operand order corrected, initialiser added. ## Description

Commit `2a83469` consolidated three separate condition walks into one, `AbilityDefinition.TryStart()`
(`AbilityDefinition.cs:50-64`). That consolidation is correct and closes **BUG-076 (b′)** and
**(c)** — see those files. Three smaller defects came with it.

```csharp
public virtual bool TryStart(AbilityContext abilityContext)
{
    if (
        (Conditions == null || Conditions.Count == 0) &&
        (Costs == null || Costs.Count == 0)
        ) return true;                                                  // :52-55
    foreach (var condition in Conditions)                               // :56
    {
        if (!condition.IsMet(abilityContext)) return false;             // :58
    }
    foreach (var cost in Costs)                                         // :60
    {
        if (cost.value > abilityContext.Services.Vital.GetCurrentStatValue(cost.statType))
            return false;
    }
    return true;
}
```

### 1. The early return is `&&`, so either loop can still run on a null list

The guard returns early only when **both** lists are empty-or-null. Two reachable shapes get past it
and then dereference a null:

| `Conditions` | `Costs` | Passes `:52-55`? | What happens |
|---|---|---|---|
| `null` | 1+ entries | yes (`&&` is false) | `:56` `foreach` over `null` → `NullReferenceException` |
| 1+ entries | `null` | yes | `:60` `foreach` over `null` → `NullReferenceException` |

The second is the live-looking one: `Costs` is declared **without** an initialiser
(`AbilityDefinition.cs:25` — `public List<StatCost> Costs;`), unlike `Conditions` (`:31`) and
`Effects` (`:34`), which both have `= new()`. This is the same asymmetry recorded in **BUG-082**.

It is latent, not live, for the same reason BUG-082 is: Unity's serializer materialises an empty
`List<T>` for a serialized list field on asset load, so a `.asset`-authored definition never
presents a null. A definition constructed in code — a test fixture, a future runtime-generated
ability — would.

### 2. The null-**element** guard was lost

The deleted `AbilityInstance.ValidateConditions()` skipped null entries:

```csharp
var condition = Definition.Conditions[i];
if (condition == null) continue;          // deleted with the method
```

`TryStart():58` calls `condition.IsMet(…)` with no such guard. A `Conditions` list holding a null or
missing-script element now throws instead of being ignored.

This is not hypothetical: **BUG-090** describes exactly that asset —
`Has Enough Mana Condition.asset` survives with a deleted script, and `ShootSpirit.asset` /
`SpiritBomd.asset` still reference it. Binding either to a slot throws here. It is dormant only
because all four Paladin assets were cleaned to `Conditions: []` in the same commit.

`AbilityInstance.Execute()` (`:143-148`) and `Casting()` (`:72`) both still guard
`if (effect == null) continue`. The conditions path is now the only one that does not.

### 3. `AbilityDefinition.CheckPayCostValid()` is dead code, and it carries the BUG-082 defect verbatim

`AbilityDefinition.cs:67-75`:

```csharp
protected virtual bool CheckPayCostValid(AbilityContext context)
{
    if (Costs.Count == 0 || Costs == null) return true;     // :69
    ...
}
```

Two problems.

**It has no callers.** `grep -rn "CheckPayCostValid" Assets/Script --include=*.cs` returns three
hits: this declaration, and a declaration + call pair inside `AbilityEffectDefinition`
(`:20`, `:24`). `AbilityEffectDefinition` does **not** derive from `AbilityDefinition` — they are
two unrelated `ScriptableObject` subclasses — so `AbilityEffectDefinition.cs:20` binds to its own
`CheckPayCostValid`, not to this one. Nothing reaches the `AbilityDefinition` copy. Its body is a
duplicate of the cost loop already inlined into `TryStart()`.

**Its guard is the BUG-082 defect, copied into a second file.** `if (Costs.Count == 0 || Costs == null)`
short-circuits left to right: `.Count` dereferences before the null test can run, so the null test is
unreachable. BUG-082 filed this at `AbilityEffectDefinition.cs:26`; it now exists at
`AbilityDefinition.cs:69` as well. Both need the operands swapped — or, better here, the whole method
deleted.

## Expected

- A null or empty list on either side is handled independently.
- A null element in `Conditions` is skipped, matching how `Effects` is treated two methods away.
- There is one `CheckPayCostValid`, and its null guard runs before the dereference.

## Fix sketch

```csharp
[Header("Cost & Cooldown")]
public float Cooldown = 1f;
public List<StatCost> Costs = new();          // :25 — match Conditions and Effects

public virtual bool TryStart(AbilityContext abilityContext)
{
    if (Conditions != null)
    {
        foreach (var condition in Conditions)
        {
            if (condition == null) continue;
            if (!condition.IsMet(abilityContext)) return false;
        }
    }
    if (Costs != null)
    {
        foreach (var cost in Costs)
        {
            if (cost.value > abilityContext.Services.Vital.GetCurrentStatValue(cost.statType))
                return false;
        }
    }
    return true;
}
```

Then delete `AbilityDefinition.CheckPayCostValid()` (`:67-75`) outright — the loop it holds is
already inlined above, and leaving it invites someone to call the wrong one.

Fix the surviving `AbilityEffectDefinition.cs:26` under **BUG-082**, which is the same one-line swap.

## Owner review — 2026-09-22: element guards added; "why swap the operands" answered

Owner question: *"bug 82 91 tại sao phải đảo toán hạng"* — why do the operands have to be swapped.

### The answer: `||` short-circuits **left to right**, so the null test never runs

```csharp
if (Costs.Count == 0 || Costs == null) return true;
//  ^^^^^^^^^^^^^^^^    ^^^^^^^^^^^^^
//  evaluated FIRST     evaluated ONLY IF the left side was false
```

C# guarantees the left operand of `||` is evaluated first, and the right operand is evaluated *only*
when the left one is `false`. So the two possible worlds are:

| `Costs` | Left operand `Costs.Count == 0` | Right operand reached? |
|---|---|---|
| a real list | evaluates fine | only if the list is non-empty — and by then the null test is pointless |
| **`null`** | **throws `NullReferenceException` on `.Count`** | **never** |

The only case the null test exists for is the one where it can never execute. It is unreachable
code wearing the costume of a guard: it reads like protection, it provides none, and it will keep
reading like protection to whoever maintains this next.

Swapping fixes it because `Costs == null` is safe to evaluate on a null reference — it *is* the null
check — and when it is `true`, `||` short-circuits and `.Count` is never touched:

```csharp
if (Costs == null || Costs.Count == 0) return true;
//  ^^^^^^^^^^^^^    never evaluated when Costs is null
```

This is the standard ordering rule: **the null test always precedes any dereference of the thing it
is testing.** Same reason `if (x != null && x.Foo)` is written in that order and never the reverse.

### It is currently latent, not live — which is why this is S3 and not S1

Unity's serializer materialises an empty `List<T>` for a serialized list field when an asset loads,
so a `.asset`-authored `AbilityDefinition` or `AbilityEffectDefinition` never presents `Costs` as
`null`. The throw needs a definition built in code — a test fixture, or a runtime-generated ability.

It is still worth the one-line swap, for the reason above: the guard currently lies about what it
does.

### Owner fix already in the working tree — element guards restored

`AbilityDefinition.TryStart()` now reads:

```csharp
foreach (var condition in Conditions)
{
    if (condition == null) continue;                    // ← added
    if (!condition.IsMet(abilityContext)) return false;
}
foreach (var cost in Costs)
{
    if (cost == null) continue;                         // ← added
    if (cost.value > abilityContext.Services.Vital.GetCurrentStatValue(cost.statType)) return false;
}
```

**This closes defect 2 of this bug** — the null-*element* guard that the deleted
`ValidateConditions()` had is back, and the `Costs` loop gained the same protection, which the
original never had. `StatCost` is a `class` (`AbilityDefinition.cs:98`), not a struct, so
`cost == null` is valid C# and compiles.

It also absorbs **BUG-090**'s one live consequence: a missing-script entry in `ShootSpirit.asset`'s
condition list now deserialises to a Unity-null element and is skipped rather than throwing.

## Owner review round 2 — 2026-09-22: item 1 re-stated, because the early return does not cover it

Owner position: *"mục 1 t trả return mà"* — item 1 is handled, the guard returns.

The guard does return, but only for **one** of the four possible shapes. The operator joining the
two halves is `&&`, not `||`:

```csharp
if (
    (Conditions == null || Conditions.Count == 0) &&     // LEFT
    (Costs      == null || Costs.Count      == 0)        // RIGHT
    ) return true;                                        // taken only when BOTH are empty

foreach (var condition in Conditions) { … }               // :56
foreach (var cost      in Costs)      { … }               // :61
```

`&&` means *"return early only if **both** lists are empty-or-null."* So the early return fires in
exactly one of the four cases:

| `Conditions` | `Costs` | LEFT | RIGHT | `LEFT && RIGHT` | returns early? | what runs next |
|---|---|---|---|---|---|---|
| null / empty | null / empty | `true` | `true` | `true` | ✅ **yes** | — |
| 2 entries | 2 entries | `false` | `false` | `false` | no | both loops run, both lists are real — fine |
| **null** | **2 entries** | `true` | `false` | **`false`** | **no** | `foreach (var condition in Conditions)` → **`NullReferenceException`** |
| **2 entries** | **null** | `false` | `true` | **`false`** | **no** | `foreach (var cost in Costs)` → **`NullReferenceException`** |

The two bottom rows are the bug. One list being null is not enough to trigger the early return when
the other list has data — and those are precisely the cases where a loop then walks a null
reference.

The guard protects the case that needs no protection (both empty: the loops would have iterated zero
times anyway and thrown nothing) and skips the two that do.

### Fix — one guard per list, not one guard for both

```csharp
public virtual bool TryStart(AbilityContext abilityContext)
{
    if (Conditions != null)
    {
        foreach (var condition in Conditions)
        {
            if (condition == null) continue;
            if (!condition.IsMet(abilityContext)) return false;
        }
    }
    if (Costs != null)
    {
        foreach (var cost in Costs)
        {
            if (cost == null) continue;
            if (cost.value > abilityContext.Services.Vital.GetCurrentStatValue(cost.statType))
                return false;
        }
    }
    return true;
}
```

The combined early return disappears entirely: an empty list iterates zero times and falls through to
`return true` on its own, so it was never needed for that case either.

Alternatively, give `Costs` the `= new()` it is missing (`:25`, item 4 of this bug) and the null
shape stops being reachable from an asset at all — but the code-constructed path (a test fixture, a
runtime-generated ability) still reaches it, so the per-list guard is the durable fix.

### Same defect, third site — `GetCostValues()`

```csharp
public void GetCostValues(StatType statType, out float cost)    // :74
{
    cost = 0f;
    foreach (var statCost in Costs)                             // :77 — no null guard at all
```

`GetCostValues()` walks `Costs` with neither a list-null guard nor an element-null guard. It is the
same shape as the two loops above and should be covered by the same fix.

### Why items 1 and 5 are moot rather than fixed

Both depended on `AbilityDefinition.Costs` or `.Conditions` being **null**. All three lists on this
class now carry an initialiser:

```csharp
public List<StatCost> Costs = new();                              // :25  ← added
public List<AbilityConditionDefinition> Conditions = new();       // :31
public List<AbilityEffectDefinition> Effects = new();             // :34
```

A field initialiser runs for every instance, including one Unity deserialises, so reaching `null`
now requires code that explicitly assigns `null` to one of them. Nothing in the repo does. The two
`foreach` loops in `TryStart()` and the one in `GetCostValues()` cannot walk a null reference any
more, so neither item can occur.

**Recommendation: do not spend sprint time on them.** What is left of item 1 is cosmetic — the
combined `&&` early return at `:52-55` is now redundant (two empty lists iterate zero times and fall
through to `return true` on their own) and slightly misleading, since it reads as a null guard while
the real protection is the initialiser three lines up. Deleting the block would make `TryStart()`
shorter and clearer, and changes no behaviour. That is a tidy-up, not a bug fix.

Item 5 stays worth one line if `GetCostValues()` is ever called on a code-constructed definition,
but the same reasoning applies.
