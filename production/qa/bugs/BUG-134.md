# BUG-134

**Title**: `EntityMoveState` wander timer is a field that `Enter()` never resets and a hard-coded `10` — authored `MoveDurationTime` is computed but never read
**Severity**: S4 (enemies wander longer than authored; carries across pooled reuse; possibly feeds a slow chase start)
**Priority**: 3 (one reset + read the computed field)
**System**: Enemy AI (state machine)
**Found by**: Friday automated QA (`qa-auto`), QA-ENT-09 run `20261117-1646` (inbox note NOTE-20261117-5); confirmed by the 2026-11-20 wrap-up triage, STATIC at `sprint-23` `0069a40c`
**Status**: Open — confirmed at runtime (automated, 1 run) and by reading code
**Fixed in**: —

## Description

`Assets/Script/Character/Entity/States/EntityMoveState.cs`:

- `:9` `private float time;` — accumulated in `LogicUpdate()` (`:26`) while no target is locked and
  reset only when it reaches the literal `10` (`:27-29`). `Enter()` (`:16-21`) does not reset it, so
  the count carries over between entries and across pooled reuse of the enemy.
- `:19-20` `moveDurationTime` / `moveTime` are computed from `EntityData.MoveDurationTime(stats)` and
  never read.

QA-ENT-09: a no-target enemy was still in `EntityMoveState` 6.5 s after spawn with
`MoveDurationTime` 5 s. A related, flaky QA-ENT-15 chase failure (`20261117-1705`) ran on a pooled
enemy whose timer had already counted. The GDD lists the literal as TD-019.

## Fix direction (owner)

Reset in `Enter()` and compare `Time.time >= moveTime` instead of the literal.

## How to verify

QA-ENT-09 PASS with the authored duration (± one frame).
