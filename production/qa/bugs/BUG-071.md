# BUG-071

**Title**: `VitalStatsComponent.RecoveryPerTimeForDuration` / `ReductionPerTimeForDuration` never run — coroutine created but never started
**Severity**: S2 (logic — every heal-over-time / damage-over-time ability effect is a silent no-op)
**System**: Abilities v2 / Player Vitals
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-09-19 (autonomous)
**Status**: PARTIAL — re-verified 2026-09-25 (HEAD `c0067f4`). **Defects 1 and 2 FIXED**: `b0b1337` added the missing `StartCoroutine`, `c0067f4` deleted the dead `count` and renamed the parameter to `timeCount`. **Defect 3 still OPEN**: the iterator recurses through the public wrapper (`VitalStatsBase.cs:81`, `:92`), so no handle is kept, nothing can `StopCoroutine` it, and a pooled enemy deactivated between ticks can throw. Severity S2 → S3. Not observable until **BUG-092** is fixed. *Previous status line:* Open

## Description

`Assets/Script/Character/Player/CoreComponent/VitalComponent.cs:63-100` (added this sprint). The public
`RecoveryPerTimeForDuration()` / `ReductionPerTimeForDuration()` compute an unused `count` local and then
call `RecoveryPerTime(...)` / `ReductionPerTime(...)`, which are `IEnumerator` methods. Calling an iterator
method without `StartCoroutine(...)` only builds the enumerator object; the body never executes.
The iterators also re-enter the public method with a decremented `timeCount` (recursion through a second
non-started coroutine), so even with `StartCoroutine` the design would not loop correctly.

## Impact

`RecoveryReductionPerTimeForDuration` effect assets (`RecoveryReductionPerTimeForDuration.cs:14,17`) do
nothing at runtime. No exception, no log — silent.

## Suggested Fix

Single coroutine: `StartCoroutine(Tick(statType, amount, perTime, duration, recover))` with an elapsed
loop (`while (t < duration) { apply; yield return new WaitForSeconds(perTime); t += perTime; }`). Guard
`perTime <= 0`.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Still open, unchanged. Two further defects in the same block are recorded here — they are
currently masked by the missing `StartCoroutine` and will surface the moment it is added.**

### The defect, confirmed

`Assets/Script/Character/Player/CoreComponent/VitalComponent.cs:63-75`

```csharp
63: public void ReductionPerTimeForDuration(StatType statType, float amount, float perTime, float duration)
65:     var count = duration / perTime;
66:     if (duration % perTime > 0) count++;
67:     ReductionPerTime(statType, amount, perTime, duration);      // iterator created, never started

70: public void RecoveryPerTimeForDuration(StatType statType, float amount, float perTime, float duration)
72:     var count = duration / perTime;
73:     if (duration % perTime > 0) count++;
74:     RecoveryPerTime(statType, amount, perTime, duration);       // iterator created, never started
```

`RecoveryPerTime` (`:77`) and `ReductionPerTime` (`:88`) are `IEnumerator` methods. Calling an
iterator method builds the state machine object and returns it; **not one line of the body
executes** until something enumerates it. There is no `StartCoroutine` on either line, and the
returned `IEnumerator` is discarded. So not even the first tick — the `Recovery(...)` /
`Reduction(...)` call at `:79` / `:90`, before any `yield` — ever runs. The effect is a complete
silent no-op, not a partial one.

C# emits no warning for discarding an iterator's return value, which is why this reads as correct.

The correct sibling is eleven lines below, in the same file:
`BuffDebuffForDuration()` (`:102-105`) does `StartCoroutine(ApplyDebuffForDuration(...))`.

### Blast radius

Sole caller of both methods:
`Assets/Script/System/Abilities/Effects/RecoveryReductionPerTimeForDuration.cs:14` and `:17`.
Every `RecoveryReductionPerTimeForDuration` effect asset — the whole heal-over-time /
damage-over-time effect type — does nothing.

### Two defects that will surface once `StartCoroutine` is added

**(a) `count` is computed and discarded; `duration` is passed where a tick count is expected.**

`:65-66` and `:72-73` compute `count` (= number of ticks) and then never use it. The recursion
parameter is named `timeCount` (`:77`, `:88`) and is decremented once per tick (`:80`, `:91`), so it
is a **tick counter** — but the callers pass `duration` into it (`:67`, `:74`). With
`duration = 6`, `perTime = 0.5`, the effect would tick 6 times over 3 seconds instead of 12 times
over 6 seconds. The intent — `count` — was computed correctly and then dropped.

**(b) The recursion re-enters the wrong method.**

`:84` — inside `RecoveryPerTime` — calls `RecoveryPerTimeForDuration(...)`, not `RecoveryPerTime`.
Same at `:95` for the reduction side. So each tick re-enters the public wrapper, which recomputes
the unused `count` and creates *another* un-started iterator. Once `StartCoroutine` is added at
`:67`/`:74`, this becomes: first tick runs, `yield return new WaitForSeconds(perTime)`, then the
recursion calls the wrapper → which (with the fix) starts a *new* coroutine → the original coroutine
then ends. It would work by accident, but every tick allocates a fresh coroutine and the chain is
impossible to `StopCoroutine`. That is the leaking-coroutine pattern explicitly forbidden by
`.claude/rules/gameplay-code.md` ("Coroutines that can leak (no `StopCoroutine` pairing)").

### Suggested fix (revised — all three at once)

Rewrite as a single self-contained loop rather than recursion, start it, and keep the handle:

```csharp
public void RecoveryPerTimeForDuration(StatType statType, float amount, float perTime, float duration)
{
    int ticks = Mathf.CeilToInt(duration / perTime);
    StartCoroutine(PerTime(statType, amount, perTime, ticks, recovery: true));
}

IEnumerator PerTime(StatType statType, float amount, float perTime, int ticks, bool recovery)
{
    for (int i = 0; i < ticks; i++)
    {
        if (recovery) Recovery(statType, amount); else Reduction(statType, amount);
        yield return new WaitForSeconds(perTime);
    }
}
```

Fixing only the `StartCoroutine` leaves (a) and (b) live, so do not split this.

Note the amount passed in is itself wrong today — see **BUG-074**, which supplies these methods with
the post-modifier total rather than the delta.

## Re-verification — 2026-09-25 (HEAD `c0067f4`) — two of three defects fixed, one remains

This bug listed three defects. Two commits landed against them.

### Defect 1 — the coroutine was never started — FIXED (`b0b1337`)

```diff
-        ReductionPerTime(statType, amount, perTime, duration);
+        StartCoroutine(ReductionPerTime(statType, amount, perTime, duration));
```

Both wrappers now start their iterator. **HoT/DoT ticks for the first time.** The code moved to
`Assets/Script/Character/Base/VitalStatsBase.cs` in the ADR-0005 refactor and is shared by the
player and by enemies, so the fix covers both sides at once.

### Defect 2 — `count` computed then discarded, seconds passed where a tick count was expected — FIXED (`c0067f4`)

```diff
-    public void ReductionPerTimeForDuration(StatType statType, float amount, float perTime, float duration)
+    public void ReductionPerTimeForDuration(StatType statType, float amount, float perTime, float timeCount)
     {
-        var count = duration / perTime;
-        if (duration % perTime > 0) count++;
-        StartCoroutine(ReductionPerTime(statType, amount, perTime, duration));
+        StartCoroutine(ReductionPerTime(statType, amount, perTime, timeCount));
     }
```

The dead `count` is gone and the parameter is renamed to what the iterator actually treats it as — a
**tick count**, decremented by one per tick (`:77`, `:88`). The unit mismatch this bug described is
resolved at the signature.

Note that it is resolved by changing the *contract*, not the code path: callers must now pass a
number of ticks. `IVitalComponent.cs:13-14` still names that parameter `duration` and was not
updated, so the interface now disagrees with every implementation of it.

### Defect 3 — the recursion re-enters the public wrapper — STILL OPEN

```csharp
IEnumerator RecoveryPerTime(StatType statType, float amount, float perTime, float timeCount)
{
    Recovery(statType, amount);                                              // :76
    timeCount--;                                                             // :77
    if (timeCount > 0)
    {
        yield return new WaitForSeconds(perTime);                            // :80
        RecoveryPerTimeForDuration(statType, amount, perTime, timeCount);    // :81 — public wrapper
    }
}
```

`:81` calls the **public wrapper**, which calls `StartCoroutine` again. Each tick therefore starts a
fresh coroutine, and the previous one ends immediately afterwards.

**Correcting the original report on one point:** this is *not* a coroutine leak. The outer iterator
reaches the end of its body right after `:81`, so exactly one coroutine is alive at a time. What is
actually wrong with it:

1. **Nothing can stop it.** No handle is kept, so there is no `StopCoroutine` pairing — the pattern
   `.claude/rules/gameplay-code.md` forbids under "Coroutines that can leak (no `StopCoroutine`
   pairing)". A DoT keeps ticking through a death, a room transition, or a pooled enemy being
   re-spawned. `EntityVitalStats.Reborn()` (`:12-20`) clears stat modifiers and movement impacts but
   has no way to cancel an in-flight tick chain.
2. **It can throw on a disabled component.** `StartCoroutine` on a disabled MonoBehaviour raises
   "Coroutine couldn't be started because the game object is inactive". A pooled enemy deactivated
   between two ticks hits exactly that path, because the restart happens *after* the
   `WaitForSeconds` instead of being one uninterrupted iterator.

**Fix** — loop instead of recursing, and keep the handle:

```csharp
private Coroutine _recoveryTick;

public void RecoveryPerTimeForDuration(StatType statType, float amount, float perTime, int timeCount)
{
    if (_recoveryTick != null) StopCoroutine(_recoveryTick);
    _recoveryTick = StartCoroutine(RecoveryPerTime(statType, amount, perTime, timeCount));
}

IEnumerator RecoveryPerTime(StatType statType, float amount, float perTime, int timeCount)
{
    for (int i = 0; i < timeCount; i++)
    {
        Recovery(statType, amount);
        if (i + 1 < timeCount) yield return new WaitForSeconds(perTime);
    }
    _recoveryTick = null;
}
```

Then add a targeted stop to `VitalStatsBase.Reborn()` so a pooled character does not inherit the
previous life's tick chain.
