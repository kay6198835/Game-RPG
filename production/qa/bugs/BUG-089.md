# BUG-089

**Title**: A refused `TryCast()` does not stop the cast — `CastInstant()` advances to `Do` anyway and `Execute()` applies every effect
**Severity**: S2 (the cost/condition gate introduced in `2a83469` can be bypassed; effects fire after being refused)
**Priority**: 2
**System**: Abilities v2 / Core
**Found by**: Post-fetch source re-verification, 2026-09-22 (branch `origin/feature/fix-player-control`, HEAD `2a83469`)
**Status**: ✅ **CLOSED 2026-09-22 — by design.** The per-effect cost flow is deliberate scaffolding for a gain-tier feature whose fields are not designed yet, and the current content is unaffected: three of the four live Paladin abilities are `Active`, and no effect asset carries `SubConditions` or `Costs`. Gaps 1, 3, 4 and 6 accepted as intended; gap 2 **withdrawn** — a refusal is meant to force-release the ability, and `CancelHold()` is the mechanism. Gap 6 promoted to a rule in `.claude/rules/weapon-skill-code.md`. Gap 7 kept as a note. No code change required; this file is the starting specification if the tier feature is picked up. *Previous status line:* ⚠️ Open (S3, dormant) — **RE-SCOPED 2026-09-22 after the owner stated the design.** Per-effect `Costs` is an upgrade-tier price: cannot afford → effect runs at default, can afford → charge and run at the gained level. Under that design `Apply()` being unconditional is **correct**, and the original claim is withdrawn. What replaces it: the tier model is **not implemented** — nothing carries "paid" through to `Apply()`, no effect has a second power level, `Costs` is one all-or-nothing bundle rather than a ladder, and a refusal calls `CancelHold()` which terminates the whole channel instead of dropping that one effect to default. Seven gaps itemised at the end of this file. Dormant: no effect asset carries `SubConditions` or `Costs`. *Previous status line:* ⚠️ Open — RE-FRAMED and DOWNGRADED S2 → S3 after owner review 2026-09-22. `Casting()` is `void` by design and the `Hold`-path claim is withdrawn; the fix sketch proposing a `bool` return is withdrawn with it. What remains is one design question — whether `TryCast() == false` should suppress `Apply()` at the `Do` phase — and it is dormant in current content (every live effect asset has an empty `SubConditions` and no `Costs`). *Previous status line:* Open — CONFIRMED by direct read of source

## Description

Commit `2a83469` renamed `Casting()` to `TryCast()` and made the refusal path call `CancelHold()`
(`AbilityInstance.cs:68-82`):

```csharp
private void Casting()
{
    foreach (var effect in Definition.Effects)
    {
        if (effect == null) continue;
        if (effect.TryCast(AbilityContext))   // :73  the gate
        {
            PayCost(effect.Costs);            // :75
        }
        else
        {
            CancelHold();                     // :79  the only consequence of a refusal
        }
    }
}
```

`CancelHold()` (`:104-108`) sets `IsHolding = false` and `CurrentHoldTime = 0f`. It returns nothing,
sets no flag the caller reads, and does not change `State`.

The caller is `CastInstant()` (`:47-55`):

```csharp
public void CastInstant()
{
    Casting();                                                  // :49  refusal happens in here
    if (Definition.ActivationType == AbilityActivationType.Hold)
    {
        if (IsHolding) return;                                  // :52
    }
    ChangeState(AbilityState.Do);                               // :54
}
```

**The refusal makes the ability advance faster, not stop.**

| Ability type | `IsHolding` after a refusal | What `:52` does | Result |
|---|---|---|---|
| `Hold` | `false` (just cleared by `CancelHold()`) | does **not** return | falls through to `:54` → `Do` |
| `Active` / any non-Hold | irrelevant, branch skipped | — | falls through to `:54` → `Do` |

On the next `HandleInput()` dispatch the state is `Do`, so `DoInstant()` (`:56-61`) runs
`Execute(AbilityContext)` — which walks `Definition.Effects` and calls `effect.Apply(context)` on
**every** effect, including the one that just refused, with no gate of any kind
(`:139-149`). The cooldown then starts as if the cast had succeeded.

So `TryCast()` returning `false` currently means: skip the per-effect cost payment, cancel the hold,
and then apply the effect anyway for free.

### Secondary: the two `IsHolding` flags desynchronise

`AbilityInstance.IsHolding` (`:12`) and `AbilityHolder.IsHolding` (`AbilityHolder.cs:19`) are
separate fields kept in step only by `AbilityHolder.StartHold()` / `.CancelHold()`
(`:138-149`), which write both. `AbilityInstance.Casting():79` calls the **instance's**
`CancelHold()` directly, so after a refusal the holder still reports `IsHolding == true` while the
instance reports `false`. `PlayerInputHandle.cs:243,273` and any UI reading the holder's flag see
stale state.

## Why this did not show up before `2a83469`

It could not. Before that commit the refusal branch did not exist: `Casting()` simply skipped
`TryPayEffectCost()` when `Casting()` returned `false` and fell through identically — but the
per-effect `Costs` lists are all empty (audited 2026-09-22: no effect `.asset` in the project
carries a serialized `Costs` list), so the gate had no observable job. `2a83469` gave the gate a
consequence (`CancelHold()`) without giving it the one that matters: stopping the cast.

## Reproduction

Blocked by **BUG-088** — the project does not compile at HEAD. Once that is fixed:

1. Author any `AbilityEffectDefinition` asset with a `SubConditions` entry that evaluates `false`,
   or with a `Costs` entry the player cannot afford.
2. Add it to a `AbilityDefinition` and bind it to `AbilitySlot.Utility`.
3. Cast it. `TryCast()` returns `false`, no per-effect cost is charged — and the effect still spawns
   its object / applies its stat change one dispatch later, and the cooldown still starts.

## Expected

A refused `TryCast()` aborts the cast: no effect is applied, no cooldown is started, and the state
machine returns to `Start` (or `Exit`) rather than advancing to `Do`.

## Fix sketch

Make the refusal visible to the caller and act on it. Minimal shape:

```csharp
private bool Casting()
{
    bool allCast = true;
    foreach (var effect in Definition.Effects)
    {
        if (effect == null) continue;
        if (effect.TryCast(AbilityContext))
        {
            PayCost(effect.Costs);
        }
        else
        {
            allCast = false;
        }
    }
    return allCast;
}

public void CastInstant()
{
    if (!Casting())
    {
        CancelHold();
        ChangeState(AbilityState.Exit);
        return;
    }
    if (Definition.ActivationType == AbilityActivationType.Hold && IsHolding) return;
    ChangeState(AbilityState.Do);
}
```

Two design points the owner has to settle first, because the code cannot infer them:

1. **All-or-nothing, or per-effect?** The sketch above refuses the whole cast if any effect refuses.
   The alternative is to let each effect gate itself — which requires `Execute()` to remember which
   effects passed `TryCast()`, not re-walk the list blindly. Consecrate is the case that decides it:
   its telegraph and its payload are one effect, so the question is only live for multi-effect
   abilities (Blessing and Avatar of Light both have two).
2. **Which flag is authoritative for `IsHolding`?** Either `AbilityHolder` stops keeping its own copy
   and forwards to the instance, or the instance stops clearing it behind the holder's back. Two
   fields for one fact is the actual defect.

## Notes

- `AbilityHolder.CancelHold()` (`AbilityHolder.cs:145-149`) is the path that keeps both flags in
  step. Routing the instance's internal cancel through the owner would fix the desync, but
  `AbilityInstance` holds `IAbilityOwner`, which does not expose `CancelHold()` — so either the
  interface grows a member or the holder stops duplicating the flag.
- Related: **BUG-079**. `Exit()`'s body is still commented out (`:63-66`), so `ChangeState(Exit)`
  leaves the instance parked in `Exit` until `AbilityHolder.StartHold()` forces it back to `Start`.
  Any fix that routes a refusal through `Exit` inherits that.

## Owner review — 2026-09-22: `Casting()` is `void` by design — fix sketch withdrawn, bug re-framed and downgraded

Owner position: *"không return nữa đây là method void"*, *"casting đã chuyển sang void"* — the
method is deliberately `void` and is not going back to returning a `bool`.

**Accepted. The fix sketch above is withdrawn** — it proposed `private bool Casting()` and a
`return` value threaded into `CastInstant()`, which is exactly the shape the owner has ruled out.
Do not implement it.

### What the owner's design actually is, read back from source

With `Casting()` returning `void`, a refusal can only be communicated through **state**, and the one
piece of state it writes is `IsHolding`:

```csharp
private void Casting()                       // :68
{
    foreach (var effect in Definition.Effects)
    {
        if (effect == null) continue;
        if (effect.TryCast(AbilityContext)) PayCost(effect.Costs);
        else                                CancelHold();      // :79
    }
}

public void CastInstant()                    // :47
{
    Casting();
    if (Definition.ActivationType == AbilityActivationType.Hold)
    {
        if (IsHolding) return;               // :52  stay in Cast while the channel runs
    }
    ChangeState(AbilityState.Do);            // :54  resolve
}
```

Read that way it is **coherent for a `Hold` ability**: you hold, `CastInstant()` re-enters each
dispatch, per-effect costs drain, and the moment an effect can no longer be cast the channel is
cancelled and the ability resolves into `Do`. "Ran out of resource mid-channel, so the channel ends
and the ability finishes" is a normal design. The original entry above read `CancelHold()` as a
failed attempt to abort; on the owner's reading it is the channel-terminator, and `:52` is doing
exactly what it should.

**That reading is withdrawn as a defect claim for the `Hold` path.**

### What remains, stated as a question rather than a finding

Two things do not follow from that design, and only the owner can say whether they are intended.

**1. For a non-`Hold` ability, a refusal has no effect at all.**

`ActivationType` is `Active` for three of the four Paladin abilities (only Blessed Slash is `Hold`).
On that path `:50-53` is skipped entirely, so `Casting()` returning through `CancelHold()` changes
nothing, and `:54` advances to `Do` identically whether every effect accepted or every effect
refused.

**2. `Execute()` has no memory of which effects refused.**

```csharp
private void Execute(AbilityContext context)     // :139
{
    for (int i = 0; i < Definition.Effects.Count; i++)
    {
        var effect = Definition.Effects[i];
        if (effect == null) continue;
        effect.Apply(context);                   // :147 — unconditional
    }
}
```

So an effect that returned `false` from `TryCast()` at the `Cast` phase still has `Apply()` called on
it at the `Do` phase, and its per-effect cost was *not* charged — it refused, so `PayCost` was
skipped. The effect fires for free.

**The question: is `TryCast()` meant to gate only the `Cast` phase, with `Apply()` always
unconditional?** If yes, this bug is by design and closes — and the rule should be written into
`.claude/rules/weapon-skill-code.md` so nobody writes an effect expecting `TryCast() == false` to
suppress `Apply()`. If no, `Execute()` needs to know, and with a `void Casting()` the natural place
is per-effect state rather than a return value.

### Verified: dormant either way, today

`TryCast()` (`AbilityEffectDefinition.cs:11-22`) can only return `false` from two sources —
`SubConditions` and per-effect `Costs`. Audited across every `.asset` under `Assets/SO/Skill/`:

| Asset | `SubConditions` | `Costs` |
|---|---|---|
| Gain For Time Effect | `[]` | absent |
| Recovery Stat Effect | `[]` | absent |
| Paladin Recovery Reduction Stats Effect (×2) | `[]` | absent |
| Paladin Spawn Slash Effect | `[]` | absent |
| Paladin Buff - Debuff Stat Effect | `[]` | absent |
| Paladin Spawn Consecrat Effect | `[]` | absent |
| **ShootSpirit** | **POPULATED** | absent |

Every live Paladin effect has an empty `SubConditions` and no serialized `Costs` key at all (the
field was added in `73ab8e7`, after the assets were authored, so Unity materialises an empty list on
load). `TryCast()` therefore returns `true` unconditionally for all of them, `CancelHold()` is never
reached, and neither question above can fire in the current content.

The single asset with a populated `SubConditions` is `ShootSpirit.asset` — and its entry points at
the deleted `HasEnoughManaCondition` (**BUG-090**), so binding it would throw in `TryStart()`
(**BUG-091**) before reaching here.

### Status

**S2 → S3, Open — pending one design answer.** Not scheduled for sprint 15: it cannot occur in
current content, and the `Hold` half of the original claim is withdrawn. It becomes live the moment
any effect asset gets a `SubConditions` entry or a `Costs` entry — which is also the moment the
answer to the question above has to exist.

The `IsHolding` desynchronisation noted in the original entry still stands on its own:
`AbilityInstance.CancelHold()` (`:104`) clears the instance's flag while `AbilityHolder.IsHolding`
(`AbilityHolder.cs:19`) stays `true`, because only `AbilityHolder.CancelHold()` (`:145-149`) writes
both. Two fields for one fact. Low severity, no current consumer of the holder's flag depends on it.

## Restated plainly — 2026-09-22, after the owner asked for a clearer explanation

Everything above is context. This section is the whole finding, in one worked example.

### The setup

Take an ability with **two** effects, and put a cost on the first one — a per-effect cost, i.e. an
entry in `AbilityEffectDefinition.Costs`, not in `AbilityDefinition.Costs`:

| | Effect | Its `Costs` |
|---|---|---|
| Effect A | a heal | 20 Mana |
| Effect B | a buff | none |

Player has **10 Mana**. Not enough for A.

### What happens, step by step

**Phase `Cast`** — `AbilityInstance.CastInstant()` calls `Casting()` (`:68-82`):

```
effect A → A.TryCast(ctx)
             → CheckPayCostValid: 20 > 10  → returns FALSE
           so:  PayCost(A.Costs) is SKIPPED     ← A's 20 Mana is never charged
                CancelHold()

effect B → B.TryCast(ctx) → TRUE
           so:  PayCost(B.Costs)               ← nothing to pay
```

Then `:54` — `ChangeState(AbilityState.Do)`.

**Phase `Do`** — `DoInstant()` calls `Execute()` (`:139-148`):

```csharp
for (int i = 0; i < Definition.Effects.Count; i++)
{
    var effect = Definition.Effects[i];
    if (effect == null) continue;
    effect.Apply(context);        // ← called on A and on B. No check of any kind.
}
```

`A.Apply()` runs. **The heal lands.**

### The result

> Effect A said "I cannot be cast, I cost 20 Mana and the player has 10."
> Its cost was not charged — correctly, it refused.
> Then it was applied anyway, at the next phase, for free.

Refusing an effect currently makes it **cheaper**, not blocked.

### Why this is a question and not a confirmed defect

There is a reading where it is intentional: `TryCast()` gates only what happens *during* the `Cast`
phase (spawning a telegraph, starting a channel), and `Apply()` at the `Do` phase is the ability
resolving, which always happens once the ability got past `CanStart()`. Consecrate is built exactly
that way — its `TryCast()` spawns the RuneCircle telegraph and its `Apply()` spawns the Lightning
payload, two different objects, one effect.

Under that reading the example above is not a bug; it is "A's Cast-phase part was refused, A's
Do-phase part still runs", and a per-effect cost is simply a charge for the Cast-phase part.

**The owner has to pick one:**

| If the answer is… | Then… |
|---|---|
| `TryCast()` gates only the `Cast` phase; `Apply()` is unconditional | This bug **closes**. Write the rule into `.claude/rules/weapon-skill-code.md` so nobody authors an effect expecting `TryCast() == false` to suppress `Apply()`, and treat per-effect `Costs` as buying the Cast phase only |
| A refused effect should not be applied | `Execute()` needs to know which effects refused. With `Casting()` staying `void`, the natural carrier is per-effect state rather than a return value — e.g. `AbilityInstance` keeping a small `HashSet<AbilityEffectDefinition>` of refusals, cleared in `BuildContext()` |

### Why it is not scheduled for sprint 15

It cannot happen in the current content. Audited every `.asset` under `Assets/SO/Skill/`:

- all seven live Paladin effect assets have `SubConditions: []` and **no serialized `Costs` key at
  all** — the field was added in `73ab8e7`, after those assets were authored, so Unity materialises
  an empty list on load
- `TryCast()` (`AbilityEffectDefinition.cs:11-22`) can only return `false` from `SubConditions` or
  `Costs`, so with both empty it returns `true` every time
- therefore `CancelHold()` at `:79` is unreachable, and the example above cannot be constructed
  without first authoring a cost or a sub-condition onto an effect asset

It becomes live the moment a designer fills either field in — which is also the moment the answer
above has to exist. That is the reason it is filed rather than dropped.

## Design intent confirmed by owner — 2026-09-22, and the flow audited against it

Owner's stated design for per-effect `Costs`:

> Per-effect cost is an **upgrade tier** (*"cột mốc sức mạnh"*). Each tier consumes an amount of
> cost. If the player cannot afford it, the effect still runs, at its **default** level. If the
> player can afford it, the cost is charged and the effect runs at its **gained** level.

That design answers the open question from the section above: `Apply()` being unconditional is
**correct**. A refused `TryCast()` means "no upgrade", not "no effect". The original framing of this
bug is therefore **withdrawn** — it was reading a tier check as a go/no-go gate.

The design is coherent. **The implementation does not deliver it.** Seven gaps, audited against
source at HEAD `2a83469` plus the current working tree.

---

### Gap 1 — `Apply()` cannot tell whether the cost was paid. Paying buys nothing.

This is the one that matters; the rest are secondary.

`AbilityEffectDefinition.Apply(AbilityContext context)` takes one parameter, and `AbilityContext`
carries no record of payment:

```csharp
Caster, Origin, Forward, TargetPoint, HoldTime, HoldRatio,
AbilityInstance, AbilityDefinition, Services
```

There is no "tier", no "gained", no "paid" flag. And every concrete `Apply()` in the project reads a
single fixed serialized value:

| Effect | What it applies | Varies with payment? |
|---|---|---|
| `SpawnProjectileEffect.Execute()` (`:26`) | `baseDamage` — `[SerializeField] protected float baseDamage = 30` (`:7`) | no |
| `SpawnSummonEffect.SummonExecute()` (`:38`) | `baseDamage + Vital.GetCurrentStatValue(PhysicalDamage)` | no — scales with the caster's stats, not with the cost |
| `StatsEffectBase.Apply()` (`:13-30`) | `statModifier.Modifiers`, a fixed `StatModifierGroup` | no |
| `BuffDebuffStatsForDuration.Apply()` (`:11`) | `statModifierGroup`, `duration` | no |

**There is exactly one power level in the code.** So:

```
player CAN afford the tier   → PayCost() charges the mana → Apply() runs at the only level there is
player CANNOT afford it      → nothing charged            → Apply() runs at the same level
```

Affording the upgrade is **strictly worse** than not affording it: same result, less mana. A player
who understood the system would deliberately keep their mana low.

**Fix requires two things, neither of which exists yet:**

1. A way to carry the outcome to `Apply()`. Options, cheapest first:
   - a field on the effect is **not** viable — effect `ScriptableObject`s are shared single instances
     (`.claude/rules/weapon-skill-code.md`), and writing per-cast state onto one is exactly BUG-077,
     which was just closed by deleting the class that did it;
   - a `Dictionary<AbilityEffectDefinition, int>` of achieved tier on `AbilityInstance`, rebuilt in
     `BuildContext()` and read through `context.AbilityInstance`;
   - or a `GainTier` field on `AbilityContext` if only one effect per ability can gain.
2. Authored data describing what the gained level *is* — a damage multiplier, an extra modifier
   group, a longer duration. Today no effect asset has a second value to move to.

---

### Gap 2 — refusing a tier cancels the whole channel instead of dropping to default

`AbilityInstance.Casting():77-80`:

```csharp
else
{
    CancelHold();          // IsHolding = false; CurrentHoldTime = 0f
}
```

`CastInstant():50-54` then reads that same flag:

```csharp
if (Definition.ActivationType == AbilityActivationType.Hold)
{
    if (IsHolding) return;      // stay in Cast — keep channelling
}
ChangeState(AbilityState.Do);   // reached, because CancelHold() just cleared IsHolding
```

So on a `Hold` ability, the first moment mana drops below the tier cost, the channel **ends**. Under
the stated design it should keep channelling at the default level.

Worse, `CancelHold()` is instance-level, not effect-level: **one** effect failing to afford its
upgrade terminates the channel for **every** effect in the ability. Blessing and Avatar of Light
both carry two effects.

Fix: a refusal should set that effect's tier to default and otherwise do nothing. `CancelHold()`
belongs to "the player released the button" (`PlayerInputHandle.cs:243,273`), not to "this effect did
not upgrade".

---

### Gap 3 — the data model has no tiers, only one all-or-nothing bundle

The design says *each* tier consumes an amount. The data says otherwise:

```csharp
public List<StatCost> Costs;                 // AbilityEffectDefinition.cs:9
public class StatCost { public float value; public StatType statType; }
```

`CheckPayCostValid()` requires **every** entry to be affordable, and `PayCost()` charges **every**
entry. So `Costs` models *"one upgrade that costs 20 Mana **and** 10 Stamina"* — a bundle of
different resources for a single step. It cannot express *"tier 1 costs 20, tier 2 costs 50, tier 3
costs 100"*.

A tier ladder needs a shape like:

```csharp
[System.Serializable]
public class AbilityGainTier
{
    public List<StatCost> Costs;     // what this tier charges
    public float PowerMultiplier;    // or a StatModifierGroup, or whatever "gained" means
}
public List<AbilityGainTier> GainTiers = new();   // ordered, index 0 = first tier above default
```

and `TryCast()` picking the **highest affordable** tier rather than answering a yes/no.

---

### Gap 4 — charged once per animation event, with no cap, for the whole hold

`Casting()` runs from `CastInstant()`, which runs from `AbilityHolder.HandleInput()`
(`AbilityHolder.cs:114-136`), which is called from `PlayerSkillWeaponState.AnimationOnAction()`
(`:47`) — a **Unity Animation Event**, via `Player.cs:78`.

> ✏️ **Correction to an earlier claim in this register and in `docs/diagrams/…§9.6`:** this was
> described as "per dispatch, frame-order dependent". That is wrong. The dispatch is animation-event
> driven, so the rate is set by the hold animation's length and is frame-rate independent. That is a
> reasonable metering mechanism, not a defect.

What is unresolved is the *semantics*: while held, each animation loop re-enters `Casting()` and
charges the tier cost again. Is a tier

- **bought once** and then held for free, or
- **sustained**, draining every animation loop while it is maintained?

Both are legitimate; the code implements the second by default, and nothing records that a tier was
already purchased. This needs to be written down before a designer fills in a `Costs` list, or the
drain rate becomes an accident of animation length.

---

### Gap 5 — the natural input for "which tier" is dead

If tiers are meant to be reached by holding longer — which is what *"cột mốc"* suggests — the natural
driver is `AbilityContext.HoldRatio`. It is **always `0f`** (**BUG-083**): a plain field snapshotted
by `BuildContext()` inside `CanStart()`, *before* `StartHold()` zeroes the counter, and never
rebuilt. All four Paladin abilities also ship `MaxHoldTime = 0`, which forces the `holdRatio = 0f`
branch at `AbilityInstance.cs:111-115` regardless.

So a charge-driven tier cannot be implemented until BUG-083 is fixed. If tiers are instead
purely cost-driven, this gap does not apply.

---

### Gap 6 — effect order silently decides who gets the mana

`Casting()` walks `Definition.Effects` in list order and charges each one as it goes. With two
effects both wanting 20 Mana and 30 available, `Effects[0]` upgrades and `Effects[1]` is refused —
and reordering the list in the Inspector reverses that, with no indication anywhere that the order is
balance-relevant.

Minor, and arguably acceptable, but it should be a stated rule rather than an emergent one.

---

### Gap 7 — on `SpawnSummonEffect`, a refused tier removes the telegraph entirely

`SpawnSummonEffect.cs:20-25`:

```csharp
public override bool TryCast(AbilityContext context)
{
    if (!base.TryCast(context)) return false;
    base.Apply(context);          // ← spawns `Prefab`: the Cast-phase telegraph
    return true;
}
```

The telegraph spawn sits **after** the gate. So for Consecrate, a player who cannot afford the tier
gets no RuneCircle at all, while `Apply()` at the `Do` phase still spawns the Lightning payload
(`:14-19`). The stated design says an unaffordable tier yields the *default* version of the effect —
not a version missing its telegraph.

`base.Apply()` is also the only thing that sets `SpawnEffectBase._context` (`:17`), which
`SpawnPos()` reads (`:43-46`). A refused `TryCast()` therefore leaves `_context` stale from the
previous cast. `SpawnSummonEffect.Apply()` happens to use `context.TargetPoint` directly (`:16`) and
so survives it, but anything added to that path would not.

### Summary

| # | Gap | Severity |
|---|---|---|
| 1 | Paying the cost changes nothing — no tier data, no channel to `Apply()` | **blocks the feature entirely** |
| 2 | A refusal cancels the whole channel instead of dropping that effect to default | high |
| 3 | `Costs` is one all-or-nothing bundle, not a tier ladder | high — data model |
| 4 | Sustain-vs-purchase semantics undefined; charged per animation event | medium — decide before authoring |
| 5 | `HoldRatio` is always `0f` (BUG-083), so charge-driven tiers cannot work | medium, only if tiers are charge-driven |
| 6 | Effect list order silently decides who can afford to upgrade | low |
| 7 | A refused tier removes the Consecrate telegraph | low, visible |

### Status

**Re-scoped, Open (S3, dormant).** The original claim ("a refused effect is applied anyway") is
**withdrawn** — that behaviour is correct under the owner's design. What replaces it is that the
gain-tier design is **not implemented**: gaps 1 and 3 mean there is nothing to gain and no tier to
reach, and gap 2 means a refusal does the wrong thing.

Still dormant and still not sprint work: every live effect asset has `SubConditions: []` and no
serialized `Costs` key, so `TryCast()` returns `true` unconditionally and none of the above can fire
today. This bug becomes the specification for the feature whenever it is picked up, rather than a
defect to patch now.

**Recommended next step when it is picked up:** write the tier model into the Abilities v2 GDD first
— tier ladder shape, purchase vs sustain, what "gained" changes, and which input selects the tier —
because gaps 1, 3 and 4 are all design decisions that the code cannot infer.

### Why none of this is live today

Verified against the assets, which is what makes the "not affected right now" claim checkable:

| Ability asset | `ActivationType` |
|---|---|
| `Avatar of Light.asset` | `0` — Active |
| `Blessing.asset` | `0` — Active |
| `Consecrate.asset` | `0` — Active |
| `Paladin Blessed Slash Ability.asset` | `1` — Hold |
| `SpiritBomd.asset` | `1` — Hold (part of the broken ShootSpirit pair, BUG-073 / BUG-090) |

Three of the four live Paladin abilities are **Active**, so the `Hold` branch at
`AbilityInstance.cs:50-53` is skipped entirely for them. And every effect asset has
`SubConditions: []` with no serialized `Costs` key, so `TryCast()` returns `true` unconditionally
and `CancelHold()` at `:79` is never reached at all.

### Rule promoted out of gap 6 — effect list order

Added to `.claude/rules/weapon-skill-code.md`: **the order of `AbilityDefinition.Effects` is
authored data, not an implementation detail.** It decides two things at once:

1. **Execution order.** `AbilityInstance.Casting()` (`:68-82`) and `Execute()` (`:139-148`) both walk
   the list in index order, so `Effects[0]` casts first and applies first.
2. **Resource priority.** `Casting()` charges each effect's cost as it goes, so `Effects[0]` has
   first claim on the player's resources and a later effect can be refused because an earlier one
   already spent them.

Reordering the list in the Inspector changes both. Treat it as a balance decision.

### Note kept for the tier feature — gap 7

`SpawnSummonEffect.TryCast()` (`:20-25`) spawns the Cast-phase telegraph **after** the gate:

```csharp
if (!base.TryCast(context)) return false;
base.Apply(context);          // spawns `Prefab` — the telegraph
return true;
```

So once per-effect costs are in use, an unaffordable tier on a summon effect will remove the
telegraph entirely while the `Do`-phase payload still fires. Under the stated design an unaffordable
tier should yield the *default* version of the effect, not a version missing its telegraph. Harmless
today — the only summon ability, Consecrate, is Active and carries no effect costs.

Related and worth carrying with it: `base.Apply()` is the only thing that sets
`SpawnEffectBase._context` (`:17`), which `SpawnPos()` reads (`:43-46`). A refused `TryCast()`
leaves `_context` stale from the previous cast. `SpawnSummonEffect.Apply()` survives it by using
`context.TargetPoint` directly (`:16`), but anything added to that path would not.

### One residual loose end — low, not reopening this bug

`AbilityInstance.IsHolding` (`:12`) and `AbilityHolder.IsHolding` (`AbilityHolder.cs:19`) are two
fields for one fact, kept in step only by `AbilityHolder.StartHold()` / `.CancelHold()`
(`:138-149`), which write both. The forced release at `Casting():79` calls the **instance's**
`CancelHold()` directly, so afterwards the holder still reports `IsHolding == true`.

It self-heals: the state has already moved to `Do`, so
`PlayerSkillWeaponState.AnimationOnAction():30-40` takes its `else` branch on the next event, and the
holder's flag is cleared when the player releases the button
(`PlayerInputHandle.cs:243` / `:273`). Worth knowing before anything new reads
`AbilityHolder.IsHolding`; not worth a fix on its own.

### Status

**Open → CLOSED (by design; scaffolding for an unimplemented feature).** No code change required.

**If and when the tier feature is picked up**, this file is the starting specification. The design
decisions the code cannot infer, in the order they have to be made:

1. What does a tier *change*? (damage multiplier, extra modifier group, longer duration — gap 1)
2. What shape holds the ladder? (`List<AbilityGainTier>` with a cost bundle and a power delta per
   tier — gap 3)
3. Is a tier bought once or sustained per animation loop? (gap 4)
4. What selects the tier — resource affordability alone, or hold duration? If hold duration, **BUG-083
   must be fixed first**: `HoldRatio` is always `0f` (gap 5)
5. How does the result reach `Apply()`? Not a field on the effect asset — those are shared single
   instances, and writing per-cast state onto one is BUG-077, which was closed by deleting the class
   that did it. A per-instance map on `AbilityInstance`, read through `context.AbilityInstance`, is
   the shape that fits (gap 1)
