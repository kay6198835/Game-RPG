# BUG-083

**Title**: `AbilityContext.HoldTime` / `.HoldRatio` are always `0f` — every charge-scaling effect is dead on arrival
**Severity**: S2 (a designed feature of Abilities v2 cannot work; currently masked because all four live abilities have `MaxHoldTime = 0`)
**Priority**: 2
**System**: Abilities v2 / Core
**Found by**: Documentation/source re-verification pass, 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)
**Status**: Open — CONFIRMED

## Description

The hold timer is accumulated *after* the only snapshot of it is taken, and nothing ever refreshes
the snapshot.

Ordering, in call order from a single button press:

| # | Site | Effect |
|---|---|---|
| 1 | `PlayerInputHandle.cs:254` | `abilityHolder.TryDoAbility(AbilitySlot.Utility)` |
| 2 | `AbilityHolder.cs:108` | `currentAbility.SetupContext()` |
| 3 | `AbilityInstance.cs:107-110` | `AbilityContext = BuildContext()` |
| 4 | `AbilityInstance.cs:117-137` | `BuildContext()` snapshots `HoldTime = CurrentHoldTime`, `HoldRatio = Clamp01(CurrentHoldTime / MaxHoldTime)` |
| 5 | `PlayerInputHandle.cs:256` → `AbilityHolder.cs:146` | `currentAbility.StartHold()` |
| 6 | `AbilityInstance.cs:102-106` | `IsHolding = true; CurrentHoldTime = 0f;` — **zeroes the counter after the snapshot** |
| 7 | `AbilityInstance.cs:32-39` | `Tick()` accumulates `CurrentHoldTime += deltaTime` every frame |

Step 7 updates `CurrentHoldTime` on the `AbilityInstance`, but `AbilityContext.HoldTime` and
`.HoldRatio` are **plain fields**, not properties:

`Assets/Script/System/Abilities/Core/AbilityContext.cs:11-12`
```csharp
public float HoldTime;
public float HoldRatio;
```

so they hold the value copied at step 4 forever. No call site rebuilds the context after
`StartHold()` — `SetupContext()` has exactly one caller (`AbilityHolder.cs:108`, step 2). Any
effect reading `context.HoldRatio` therefore sees `0f` on every cast, no matter how long the button
is held.

Even if the ordering were corrected, step 4's `holdRatio` computation would still be `0f`, because
it divides the just-zeroed (or not yet accumulated) `CurrentHoldTime`.

## Why nobody has noticed

`MaxHoldTime` is `0` on all four live Paladin ability assets, and `BuildContext()` guards
`if (Definition.MaxHoldTime > 0f)` before computing the ratio, so `HoldRatio` is legitimately `0`
today regardless. The bug surfaces the moment a designer sets a non-zero `MaxHoldTime` — the
feature will simply not respond, with no error.

Note also the history: a charge-scaling feature was already reverted once
(`48a1060 Revert "feat(abilities): charge-scaling effects — hold longer, deal more damage"`,
still sitting in `stash@{0}`).

## Suggested Fix

Two options; pick one and record it in the Abilities v2 GDD (demo-checklist item 21):

- **A (minimal)** — make `AbilityContext.HoldTime` / `.HoldRatio` computed properties that read
  through to `AbilityInstance` (already referenced at `AbilityContext.cs:14`), so they are always
  live rather than snapshotted.
- **B** — call `SetupContext()` again at the start of `TryCastInstant()` / `TryDoInstant()`, after
  the hold has accumulated. More allocation per cast, and it resets `Origin`/`Forward`/`TargetPoint`
  mid-cast, which may or may not be wanted — that is a design decision, not a code decision.

Either way, move `StartHold()` before `SetupContext()` so the counter is not zeroed after being
read.

## Re-verification — 2026-09-22 (post-fetch, HEAD `2a83469`) — **still open, mechanism slightly changed**

`2a83469` reshaped context construction but did not fix this. `SetupContext()` was deleted and
`BuildContext()` became `private void`, assigning the field directly (`AbilityInstance.cs:109-129`).
It is now called from exactly one place:

```csharp
public bool CanStart()                       // :89
{
    if (CooldownRemaining > 0f) return false;
    if (Owner == null) return false;
    BuildContext();                          // :93 — the only call
    if (!Definition.TryStart(AbilityContext)) return false;
    return true;
}
```

The ordering defect is unchanged, and is now easier to state:

```
PlayerInputHandle.cs:254  AbilityHolder.TryDoAbility()
                            :107  CanStart()  →  BuildContext()   ← HoldTime snapshotted here
PlayerInputHandle.cs:256  AbilityHolder.StartHold()
                            :141  AbilityInstance.StartHold()     ← CurrentHoldTime = 0f
                          Tick() increments CurrentHoldTime each frame
                          …nothing rebuilds AbilityContext…
                          Effects read ctx.HoldTime / ctx.HoldRatio  →  always 0f
```

`AbilityContext.HoldTime` / `.HoldRatio` are still plain fields (`AbilityContext.cs:11-12`), not
properties, so the snapshot cannot track the counter.

Still masked in content: all four Paladin abilities have `MaxHoldTime = 0`, so `holdRatio` would be
`0f` from the `:112` branch regardless.

**Status: unchanged — Open.** Fix is unchanged: make `HoldTime` / `HoldRatio` computed properties
reading back through `AbilityInstance`, or rebuild the context at each `CastInstant()` dispatch.
