# BUG-081

**Title**: Two `INegativeReceiver` implementations on the player prefab with byte-identical bodies — which one runs depends on which collider is hit
**Severity**: S2 (architecture / non-deterministic dispatch; no crash today)
**Priority**: 2
**System**: Player / Damage chain
**Found by**: Documentation/source re-verification pass, 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)
**Status**: ✅ FIXED 2026-09-25 (ADR-0005 refactor, merged in `379c267`) — exactly one `INegativeReceiver` implementer remains (`NegativeReceiverBase<TCore>`); `ResourceReceiver` dropped the interface; both enemy prefabs carry **0** references to the player receiver. *Previous status line:* Open — CONFIRMED

## Description

`NegativeReciver.TakeDamage()` and `ResourceReceiver.TakeDamage()` are the same method, character
for character:

`Assets/Script/Character/Player/CoreComponent/NegativeReciver.cs:5-11`
```csharp
public void TakeDamage(float amoutDamage, Vector2 attackPosition)
{
    Core.GetCoreComponent(out VitalStatsComponent vitalStatsComponent);
    vitalStatsComponent.Reduction(StatType.HP, amoutDamage);
    Core.GetCoreComponent(out PlayerInputHandler input);
    input.OnTakeDamage(attackPosition);
}
```

`Assets/Script/Character/Player/CoreComponent/ResourceReceiver.cs:29-35` — identical body.

Both classes implement `INegativeReceiver`, and **both components are present on the player
prefab**. Verified by GUID:

| Script | GUID | Present in |
|---|---|---|
| `NegativeReciver.cs` | `67338086a6ba0854686235682f860347` | `Assets/Prefab/Player/PlayerTest.prefab`, `Assets/SO/Database/EnemyPrefab.prefab` |
| `ResourceReceiver.cs` | `8fb8184d4f0d42944ac180fbd83c833a` | `Assets/Prefab/Player/PlayerTest.prefab` |

Every damage source in the project resolves the receiver off the collider it hit
(`MeleeWeapon.OnActivate()`, `bullet.cs`, `Projectile.CheckCollisions()`,
`EntityWeapon.Attack()`), so which of the two runs is decided by the prefab's collider layout, not
by design. Today the two bodies are identical, so the outcome is the same either way — which is
exactly what makes this a latent trap: the next edit to one of them silently creates two different
damage behaviours on the same character.

This is the player-side twin of **BUG-053** (two `INegativeReceiver` implementations on the enemy),
which shipped broken for six sprints for the same reason. `.claude/rules/ai-code.md` already states
the rule for the enemy side ("`EntityNegativeReciver` is the **single** `INegativeReceiver`
implementer on an enemy. Do not add a second one"); no equivalent rule exists for the player.

## Secondary finding — player component on an enemy prefab

`Assets/SO/Database/EnemyPrefab.prefab` carries `NegativeReciver` (the **player** component, a
`CoreComponent<Core>`) and does **not** carry `EntityNegativeReciver`
(GUID `67371b05b76c96447af52322cb34d199`, 0 occurrences). `NegativeReciver` resolves its hub via
`GetComponentInParent<Core>()`, which on an enemy hierarchy returns null. If that prefab is ever
spawned, it repeats BUG-053's exact failure. Needs an owner decision on whether the prefab is live
or a dead template.

## Suggested Fix

Pick one player-side `INegativeReceiver` implementer (BUG-053's precedent says: the one that owns
nothing else) and delete `TakeDamage()` from the other. `ResourceReceiver`'s stated job is
pickup/buff/recovery (`IResourceReceiver`); damage reception belongs on `NegativeReciver`. Then
remove the `INegativeReceiver` interface from `ResourceReceiver`'s declaration so the compiler
prevents a third one, and add the player-side rule to `.claude/rules/gameplay-code.md`.

Separately: remove `NegativeReciver` from `EnemyPrefab.prefab`, or delete the prefab.

## Re-verification — 2026-09-25 (HEAD `c0067f4`) — FIXED by the ADR-0005 refactor

Both halves of this bug are closed.

### Half 1 — two `INegativeReceiver` implementers on the player

There is now exactly **one** implementer in the whole tree. Grepping the interface at this HEAD:

| File | Role |
|---|---|
| `Assets/Script/Character/Base/NegativeReceiverBase.cs:7` | `public abstract class NegativeReceiverBase<TCore> : CoreComponentBase<TCore>, INegativeReceiver` — the only implementer |
| `Assets/Script/Character/Player/CoreComponent/NegativeReciver.cs:3` | `NegativeReciver : NegativeReceiverBase<Core>` |
| `Assets/Script/Character/Entity/CoreComponent/EntityNegativeReciver.cs:3` | `EntityNegativeReciver : NegativeReceiverBase<EntityCore>` |

`ResourceReceiver` dropped the interface entirely — it is `: Interact` and nothing else (see
BUG-080). The byte-identical second body that made "which one runs" depend on collider layout no
longer exists, so the ambiguity is gone by construction, not by prefab surgery.

`PlayerTest.prefab` still carries **both** components (1 GUID reference each), and that is now
correct: `NegativeReciver` is the hurtbox receiver, `ResourceReceiver` is the pickup interactor.
They no longer answer the same call.

### Half 2 — `EnemyPrefab.prefab` carrying the player receiver
