# BUG-079

**Title**: `AbilityInstance` never leaves `AbilityState.Exit` — `Exit()` is an empty method with its only statement commented out
**Severity**: S3 (architecture — reset lives in the wrong layer; the original "castable once per scene load" consequence was wrong, see re-verification 2026-09-22. Originally filed S2)
**Priority**: 3
**System**: Abilities v2 / Core
**Found by**: Manual code review of the Abilities v2 architecture, 2026-09-21 (`origin/feature/fix-player-control`, HEAD `15242e6`)
**Status**: Open — re-verified 2026-09-25 (HEAD `c0067f4`), **S3, dormant and unchanged**. `AbilityInstance.Exit():63-66` is still commented out. The enemy path added by ADR-0005 Amendment 2 was checked and does **not** widen the exposure: `EntityAbilityState.Enter():27` calls `StartHold()`, so enemies get the same forced reset the player gets. *Previous status line:* Open — CONFIRMED 2026-09-22. Consequence corrected and severity lowered; see re-verification.

## Description

`Assets/Script/System/Abilities/Core/AbilityInstance.cs:72-75`:

```csharp
public void Exit()
{
    //ChangeState(SkillState.Start);
}
```

The reset is commented out (and still names the removed `SkillState` enum, now `AbilityState`).
`State` advances `Start → Cast → Do → Exit` and then stays at `Exit` forever.

`AbilityHolder.HandleInput()` switches on `instance.State`; the `Exit` branch calls this no-op, so a
second activation of the same `AbilitySlot` finds the instance already in `Exit` and does nothing.
The only code path that writes `Start` back is `AbilityHolder.StartHold()` (line 147), which
`PlayerInputHandler` calls only for hold-type input — so `AbilityActivationType.Active` abilities such
as Consecrate have no reset path at all.

Interacts with BUG-069 (`CanStart()` cooldown gate has no callers): together, the instance's cooldown
and its phase state are both effectively unmanaged.

## Suggested Fix

Restore the reset, using the current enum name:

```csharp
public void Exit()
{
    ChangeState(AbilityState.Start);
    CancelHold();
}
```

and gate re-entry on `CanStart()` in `AbilityHolder.TryDoAbility()` so the cooldown is actually enforced.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Still open. The defect is real; the consequence recorded in this file was wrong, and the severity
is lowered from S2 to S3 accordingly.**

### The code is unchanged

`Assets/Script/System/Abilities/Core/AbilityInstance.cs:73-76`

```csharp
public void Exit()
{
    //ChangeState(SkillState.Start);
}
```

Note the commented line still names **`SkillState`**, the pre-promotion name of the enum. The enum
has been `AbilityState` since the framework left `prototypes/` (`AbilityDefinition.cs:74-80`), so
the commented statement would not even compile if uncommented as written.

Sole caller: `AbilityHolder.cs:137-139`, the `case AbilityState.Exit:` arm of `HandleInput()`.

### Correction — the ability is NOT bricked

This file (and `CLAUDE.md`, and `docs/diagrams/ability-system-diagrams.md:226,248`) states that
`State` never returns to `Start`, so an `Active` ability is "castable once per scene load". **That
is not what happens.** The state is reset from a different layer:

`AbilityHolder.cs:143-148`
```csharp
public void StartHold()
{
    IsHolding = true;
    currentAbility.StartHold();
    currentAbility.ChangeState(AbilityState.Start);      // <-- forced reset
}
```

`StartHold()` is called on every fresh button press, from `PlayerInputHandle.cs:254-256`:

```csharp
if (abilityHolder.TryDoAbility(AbilitySlot.Utility))
{
    abilityHolder.StartHold();
```

So each new press unconditionally drives the instance back to `AbilityState.Start`, and abilities
are re-castable. The "once per scene load" claim should not be repeated.

### What the bug actually is

A **layering defect**, not a functional lock: the ability's own state machine cannot reset itself,
and depends on an outside caller (`AbilityHolder.StartHold()`) to do it for it. Consequences:

- `AbilityInstance.Exit()` is dead weight; the `case AbilityState.Exit:` arm does nothing.
- The reset is coupled to the *hold* entry point. Any future activation path that does not go
  through `StartHold()` — a passive ability, an AI-driven cast, a queued cast — will get a stuck
  instance, because there is no other reset.
- The reset is also why the `AbilityState.Exit` phase has no observable meaning: nothing can be
  cleaned up there.

### Related shared-state note previously attached to this ID

`.claude/rules/weapon-skill-code.md` cites "`SpawnEffectBase._context` / `.dir` (BUG-079)" as an
example of per-cast state stored on a shared `ScriptableObject`. That observation is correct but
belongs with **BUG-078**, where the `_context` coupling is load-bearing. The rules file is corrected
in the same 2026-09-22 pass.

## Suggested Fix (revised)

Uncomment and correct the enum name so the instance owns its own reset:

```csharp
public void Exit()
{
    ChangeState(AbilityState.Start);
}
```

then remove the `ChangeState(AbilityState.Start)` line from `AbilityHolder.StartHold()`, so reset
lives in exactly one place. Verify that `HandleInput()` still reaches the `Exit` arm before the next
press — if it does not, the arm and the method should both go.

### The enemy path was checked and it does not make this worse

ADR-0005 Amendment 2 gave enemies the same framework (`EntityAbilityHolder : AbilityHolderBase<EntityCore>`).
The obvious worry — a second activation path that skips `StartHold()` and inherits a stuck instance —
**does not apply**: `EntityAbilityState.Enter():27` calls `abilityHolder.StartHold()`, exactly as the
player's input path does, so the enemy gets the same forced reset. And `LogicUpdate():61-63` leaves
the state on `AbilityState.Exit` by changing to `IdleState`, so nothing spins on the empty `Exit()`.

That closes the hazard this bug flagged as hypothetical, for the one new caller that arrived. What
remains is the original layering complaint only: the instance still cannot reset itself, and every
new driver has to remember to call `StartHold()` to get one.

**Status**: unchanged — Open, **S3**, dormant. One-line uncomment, plus fixing the stale `SkillState`
name in the comment while the file is open.
