# BUG-072

**Title**: Summon-type ability damage (`SpawnSummonEffect.SummonExecute`) has no target resolution — uses `Services.NegativeReceiver`, which is null or a stale value
**Severity**: S2 (logic — Paladin Consecrate / Lightning summon cannot damage enemies)
**System**: Abilities v2 / Spawn effects
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-09-19 (autonomous)
**Status**: Open — CONFIRMED 2026-09-22 (static read; not run in Play Mode). Scope widened: no Abilities v2 effect can deal damage at all — see re-verification.

## Description

`SpawnSummonEffect.cs:33-41`: `SummonExecute` reads `currentContext.Services.NegativeReceiver` and calls
`TakeDamage(...)` on it. Nothing in the summon path ever sets that field — only
`SpawnProjectileBase.cs:31-32` writes it, from an `OnTrigger` hit, into the *shared* services object.
`LightningController.Execute()` (`LightningController.cs:12-19`) contains only a comment
("get collider in a range / get INegative / foreach ...") then calls `base.Execute()`, i.e. the target
query was never written. Result: either a null receiver (no damage) or whichever target a previous
projectile last touched (stale, wrong target).

## Suggested Fix

In `LightningController.Execute()` do the `OverlapCircleNonAlloc` with a cached buffer and configured
`LayerMask`, invoke the callback per hit `INegativeReceiver`; make `SummonExecute` take the receiver as an
argument instead of reading a shared mutable service field.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Status raised from PLAUSIBLE to CONFIRMED, and the scope is far larger than this file records.**

### The decisive fact — `Services.NegativeReceiver` is permanently null

A project-wide search for writers of `IAbilityServices.NegativeReceiver` returns exactly **one**
site in the whole repository:

`Assets/Script/System/Abilities/Runtime/SpawnMono/SpawnProjectileBase.cs:32`
```csharp
_context.Services.NegativeReceiver = negativeReciver;
```

That line is inside `OnTriggerEnter(Collider other)` (`:29`) — the **3D** trigger callback, which
Unity never dispatches for this class's `Rigidbody2D` + `CircleCollider2D` pair (**BUG-075**). The
only writer is inside a method that never runs.

The `AbilityServices` constructor does not assign it either:

`Assets/Script/System/Abilities/Core/AbilityContext.cs:37-47`
```csharp
public AbilityServices(IObjecPoolService pool, IPlayerStatService stats,
                       IResourceReceiver resourceReceiver, IVitalComponent vital)
{
    Pool = pool; Stats = stats; ResourceReceiver = resourceReceiver; Vital = vital;
}   // NegativeReceiver is never set
```

`NegativeReceiver` is declared `{ get; set; }` (`:26`, `:35`) — the only one of the five services
that is mutable — precisely so the projectile could stash a hit target in it. Its single writer is
dead.

Sole construction site: `AbilityHolder.Setup()` (`AbilityHolder.cs:48`).

### Consequence — no Abilities v2 effect can deal damage, at all

Both damage-dealing effects read that field and are guarded against null, so they no-op **silently**:

| Site | Code |
|---|---|
| `SpawnSummonEffect.cs:33-41` | `var negativeReceiver = currentContext.Services.NegativeReceiver; if (negativeReceiver != null) { ... TakeDamage(...) }` |
| `SpawnProjectileEffect.cs:21-28` | same shape |

Abilities v2 is the player's **only** ability path (Abilities v1 is the weapon/enemy path). So at
HEAD, no player ability deals any damage, and nothing in the Console says so.

This is the single most consequential finding in the project and was recorded nowhere before
2026-09-22.

### Secondary — the summon still has no target query

`Assets/Script/System/Abilities/Runtime/SpawnMono/LightningController.cs:12-19` is unchanged:

```csharp
public override void Execute()
{
    // get colider in a range
    // get INegative
    // foreach INegative _callback.Invoke(_context);

    base.Execute();
}
```

Three comment lines where the target resolution should be. `RuneCircleController` is an empty body.

### Root cause is architectural, not a typo

`SpawnMono`'s callback type is `Action<AbilityContext>` (`SpawnMono.cs:9`, `:11`, `:15`). There is
no parameter on that signature for "the thing that was hit". A spawned object therefore has no
channel to hand its hit target back to the effect, which is why `SpawnProjectileBase` had to smuggle
it through a mutable field on the shared `AbilityServices` instance in the first place. Fixing
`OnTriggerEnter` → `OnTriggerEnter2D` (BUG-075) would restore *projectile* damage but leaves the
design flaw: a single shared field holding per-hit state, overwritten by whichever object last hit
something, and read by a summon that never writes it.

### Suggested fix (revised)

Change the callback to carry its target, e.g.
`Action<AbilityContext, INegativeReceiver>` or a small `AbilityHitInfo` struct, and remove the
`NegativeReceiver` setter from `IAbilityServices` entirely so the shared-state path is not
reachable. Then implement `LightningController.Execute()`'s overlap query against the configured
layer mask (`Physics2D.OverlapCircleNonAlloc` into a cached buffer, per
`.claude/rules/engine-code.md`).

Blocked with BUG-075, BUG-076 and BUG-078 on the missing Abilities v2 GDD — the callback contract
is a design decision.

## Owner review — 2026-09-22 — scope CORRECTED, escalation withdrawn

**Owner's position:** `SummonExecute` is a callback invoked elsewhere, *after* the invoking code has
set `context.Services.NegativeReceiver`. The `if (negativeReceiver != null)` guard is therefore
deliberate — act if a receiver is present, skip if not.

**Verified, and the owner is right.** The re-verification section above framed this as an
architectural defect ("the callback signature cannot carry a target — that is a design flaw, not a
typo"). That framing is **withdrawn**. The set-then-invoke pattern is intentional and already
implemented correctly on the projectile side:

```csharp
// SpawnProjectileBase.cs:31-33 — the reference implementation of the pattern
other.TryGetComponent<INegativeReceiver>(out INegativeReceiver negativeReciver);
_context.Services.NegativeReceiver = negativeReciver;   // set
_callback.Invoke(_context);                             // then invoke
```

The write and the invoke are adjacent and synchronous, so there is no interleaving window and no
"overwritten by whichever object last hit" hazard within a frame. The earlier claim to the contrary
was wrong.

The invoke wiring on the summon side also exists and is correct:

| Line | Code |
|---|---|
| `SpawnSummonBase.cs:12-15` | `public virtual void Execute() { _callback.Invoke(_context); }` — called by a Unity Animation Event |
| `LightningController.cs:18` | `base.Execute();` — so the callback *does* fire |

**What is actually missing is one thing: the target query.**
`LightningController.Execute()` (`:12-19`) still contains only the three comment lines that would
set the receiver before invoking:

```csharp
public override void Execute()
{
    // get colider in a range
    // get INegative
    // foreach INegative _callback.Invoke(_context);

    base.Execute();
}
```

`base.Execute()` fires the callback once, with `Services.NegativeReceiver` never having been
assigned on this path — so `SummonExecute` (`SpawnSummonEffect.cs:33-41`) correctly skips. Behaving
exactly as designed, with the input never supplied.

**Corrected scope — back to what this bug was originally filed as:** summon-type abilities have no
target resolution. `RuneCircleController` (an empty subclass) does not override `Execute()` at all,
which is correct for a telegraph that deals no damage (see BUG-078).

**Corrected severity/impact statement.** Still true and unchanged:
`Services.NegativeReceiver` is null at runtime today, because the only writer
(`SpawnProjectileBase.cs:32`) sits in a 3D callback Unity never dispatches (BUG-075), and no summon
writes it at all. So no Abilities v2 effect deals damage at HEAD. **But that is two independent
implementation gaps, not one design flaw:**

| Path | Why no damage | Fix |
|---|---|---|
| Projectile | `OnTriggerEnter(Collider)` is the 3D signature — never dispatched | **BUG-075**, one word |
| Summon | target query unimplemented (3 comment lines) | **this bug** |

Fixing BUG-075 restores projectile damage on its own. It does not depend on this bug, and this bug
does not depend on a signature change.

**Suggested fix (revised).** Implement the commented loop, following the projectile's pattern and
`.claude/rules/engine-code.md` (NonAlloc, cached buffer, Inspector layer mask):

```csharp
public override void Execute()
{
    int n = Physics2D.OverlapCircleNonAlloc(transform.position, radius, _buffer, layerMask);
    for (int i = 0; i < n; i++)
    {
        if (!_buffer[i].TryGetComponent<INegativeReceiver>(out var receiver)) continue;
        _context.Services.NegativeReceiver = receiver;
        _callback.Invoke(_context);
    }
}
```

`radius` and `layerMask` belong on the controller as `[SerializeField]`, not hardcoded.

**Retracted alongside this:** TD-046 ("shared mutable state / callback signature is the root cause")
is corrected in `docs/tech-debt-register.md` — the signature is adequate for the intended pattern.
