# BUG-069

**Title**: `AbilityInstance.CanStart()` (cooldown gate) has zero callers — abilities can be spammed with no cooldown enforcement
**Severity**: S2 (balance/logic — no crash, but a core mechanic of the new ability system does not function as designed)
**System**: Abilities v2 / Player
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-09-13 (autonomous, `lead-programmer` agent via `/code-review`)
**Status**: FIXED — verified 2026-09-22 (see re-verification below)

## Description

`Assets/Script/System/Abilities/Core/AbilityInstance.cs:98` defines `CanStart()`, which checks
`CooldownRemaining <= 0`. Confirmed via project-wide search: this method has **no callers**.
`AbilityHolder.HandleInput()` (`Assets/Script/Character/Player/CoreComponent/AbilityHolder.cs:94`)
dispatches purely on the current `SkillState`, and
`PlayerInputHandler.OnSkillWeapon()` (`PlayerInputHandle.cs:244-249`) calls `StartHold()`, which
unconditionally does `currentAbility.ChangeState(SkillState.Start)` regardless of
`CooldownRemaining`. The cooldown timer still ticks (visible in `AbilityDefinition.Cooldown` /
`AbilityInstance`'s internal timer), but nothing ever reads it to block re-activation.

## Impact

- Every player ability (Primary/Secondary/Utility/Ultimate) can currently be re-triggered on the
  next frame after finishing, with no cooldown wait — a core piece of the Abilities v2 design
  (`AbilityDefinition.Cooldown`) is dead code in the activation path.
- Directly affects combat balance/testing for any playtest session run against the current build.

## Suggested Fix

Call `CanStart()` (or equivalent) at the top of `AbilityHolder.HandleInput()` / wherever
`ChangeState(SkillState.Start)` is triggered, and no-op (or play a "can't activate" feedback) when
it returns `false`. Pairs naturally with BUG-068 — both are gaps in the same activation entry point
and could be fixed in the same pass.

## Resolution Note — 2026-09-19 (`pm-weekly-wrapup`)

**Apparently fixed (incidental, unverified).** `AbilityHolder.TryDoAbility()` (`AbilityHolder.cs:~107`) now
calls `currentAbility.CanStart()` before activation and `PlayerInputHandle.cs:~254` gates `StartHold()`
behind it. Landed as a side effect of off-plan ability rework, not a targeted fix. Not confirmed in Play
Mode, no test. Left open pending S14-07-style verification. Caveat: input is hardcoded to
`AbilitySlot.Utility`; Primary/Secondary/Ultimate slots are unreachable from input.

## Re-verification — 2026-09-22 (branch `main`, HEAD `d17fcc5`, merge of `e2cb75e`)

**Status changed: Open → FIXED.** The 2026-09-19 note above called this "apparently fixed
(incidental, unverified)". The full enforcement loop now reads closed end to end in source, so the
qualifier is removed.

### Evidence — the complete cooldown cycle

| Step | File:line | Code |
|---|---|---|
| Gate is called | `AbilityHolder.cs:107` | `if (!currentAbility.CanStart()) return false;` inside `TryDoAbility()` |
| Gate logic | `AbilityInstance.cs:95-100` | `if (CooldownRemaining > 0f) return false;` |
| Timer is set | `AbilityInstance.cs:192-195` | `StartCooldown()` → `CooldownRemaining = Definition.Cooldown` |
| Set is reached | `AbilityInstance.cs:69` | `StartCooldown()` called in `TryDoInstant()` |
| Timer is ticked | `AbilityInstance.cs:23-30` | `Tick(float deltaTime)` decrements and clamps at `0f` |
| Tick is driven | `AbilityHolder.cs:51-59` | `Processing()` iterates `_equipped` and calls `pair.Value.Tick(dt)` |
| Driver is ticked | `PlayerBasicState.cs:32`, `PlayerSkillWeaponState.cs:68` | `abilityHolder.Processing()` in `LogicUpdate()` |
| Entry point is gated | `PlayerInputHandle.cs:254` | `if (abilityHolder.TryDoAbility(AbilitySlot.Utility))` wraps `StartHold()` |

Every link in the original bug's "no enforcing caller" claim is now present.

### Residual — recorded, not reopened

`Processing()` is only reached from `PlayerBasicState.LogicUpdate()` and
`PlayerSkillWeaponState.LogicUpdate()`. While the player is in any state outside that pair
(`PlayerTakeDamageState`, `PlayerEquidUnequid`, `PlayerIntertorState`,
`PlayerResourceReceiverState`, `PlayerDeathState`), `Tick()` does not run and `CooldownRemaining`
does not decrease. That makes cooldowns **longer** than authored in those states, never shorter — it
fails in the safe direction, so it is not a reopen. Worth a note in the Abilities v2 GDD when one
exists (demo-checklist item 21).

### Caveat carried forward unchanged

Input is still hardcoded to `AbilitySlot.Utility` (`PlayerInputHandle.cs:254`). Primary, Secondary
and Ultimate remain unreachable from input. That is a separate gap, not part of this bug.

**Still not confirmed in Play Mode.** The verdict above is a static read of a now-complete call
chain, which is a materially stronger claim than the 2026-09-19 note, but is not a runtime test.
