# BUG-063

**Title**: `Stat.modifiers` re-serialized via `#if UNITY_EDITOR [SerializeField]` — reopens a previously-fixed data-corruption bug (undoes `f5de65a`)
**Severity**: S1 (active data-corruption risk on checked-in `.asset` files)
**System**: StatSystem
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-08-22 (autonomous, `lead-programmer` agent via `/code-review`)
**Status**: ⏸️ ACCEPTED (deferred) 2026-09-22 by owner decision — the `[SerializeField]` stays while the stat system is under development and is removed at demo prep. Not a neglected fix; see the decision block at the end of this file for the cost and the mitigation. *Previous status line:* Open — re-verified unchanged 2026-09-06 (`pm-weekly-wrapup`, `sprint-12` HEAD `f3f5f08`).
`Stat.cs:63-65` still reads `#if UNITY_EDITOR` / `[SerializeField]` / `#endif` directly above
`modifiers`, byte-for-byte the same block flagged at every check since Sprint 10. This is now the
single most persistently carried open item in the project (24+ consecutive triage/standup cycles
with a documented one-line fix and zero technical blocker).

## Description

`Assets/Script/StatSystem/Stat.cs:63-66` currently reads:

```csharp
#if UNITY_EDITOR
[SerializeField]
#endif
private List<StatModifier> modifiers = new List<StatModifier>();
```

This was introduced by commit `aa4e620` ("fix conflict DI", a merge-conflict resolution), landing
89 minutes before this review caught it. It directly undoes commit `f5de65a` ("fix(stats): stop
serializing Stat.modifiers so runtime buffs cannot leak"), which itself was the fix for a real,
previously-shipped incident: `STR +1 Flat` (a runtime buff) leaked into `PlayerStats.asset` /
`Test.asset` and was committed to the repo. CLAUDE.md's `NEW-4` entry documents that original fix and
explicitly warns:

> A warning comment above the field records the past leak... and the distinction from
> `StatModifierGroup.authoredModifiers`, which **must stay serialized**

The block comment sitting directly above this field in `Stat.cs` itself still says (per the code
review agent's reading) not to add `[SerializeField]` back — the guardrail comment is correct and
current, but the code next to it now contradicts it. `StatsSO.OnEnable()`'s comment claiming this
field "no longer serializes so this loop is theoretically a no-op" is now also factually wrong about
the code it sits beside.

`UNITY_EDITOR` is defined in every Editor session — exactly where designers author `.asset` files,
and exactly the condition under which the original leak happened. Gating the attribute behind
`#if UNITY_EDITOR` does not avoid the bug; it reproduces it in the only environment where it can
actually corrupt a checked-in asset.

## Impact

- Any runtime buff applied to `Stat.modifiers` while the Editor is in Play Mode risks being
  serialized into `PlayerStats.asset` or `Test.asset` again, exactly reproducing the incident
  `f5de65a` fixed.
- `ADR-0001` (StatSystem dual data structure) states this constraint explicitly as part of its
  accepted Decision — this is an **architectural violation**, not just a stylistic regression.
- No EditMode test exists to catch this class of regression (see `tests/EditMode/` — `.gitkeep` only,
  TD-014), which is why it landed silently in a merge-conflict resolution and went unnoticed for
  89 minutes until this review.

## Suggested Fix

Remove the `#if UNITY_EDITOR [SerializeField] #endif` block entirely, restoring the bare private
field exactly as `f5de65a` left it. Recommend pairing the fix with a one-line EditMode test that
asserts `Stat.modifiers` carries no `SerializeField` attribute (via reflection), so this can't
regress silently a third time — this is the second time this exact field has needed the fix.

### Correction — `#if UNITY_EDITOR` is not a partial mitigation

`CLAUDE.md`'s Known Bugs row and several sprint notes describe the preprocessor guard as narrowing
the blast radius. It does not narrow it at all, and repeating that framing is why this has been
carried for 29+ cycles without anyone spending the sixty seconds the fix takes.

`UNITY_EDITOR` is defined **in the Unity Editor, including Play Mode.** Play Mode in the Editor is
precisely the situation the bug describes:

1. Designer enters Play Mode. Runtime buffs are added to `Stat.modifiers`.
2. `UNITY_EDITOR` is defined, so `modifiers` is a serialized field.
3. Unity marks the owning `BaseStatsSO` asset dirty and writes the live buff list into
   `PlayerStats.asset` / `Test.asset` / an `Enemy/*Stats.asset`.
4. The modified `.asset` is committed.

That is the exact incident recorded in the file's own comment block immediately above the guard
(`Stat.cs:49-62`), which documents a "STR +1 Flat" modifier reaching `PlayerStats.asset` and
`Test.asset` and having to be cleaned by hand on `sprint-10` (2026-08-20). The comment states in
capitals that `[SerializeField]` must never be added to this field, **under any preprocessor
guard** — and the attribute is sitting directly beneath it.

What the guard actually protects is the **player build**, where `.asset` files are packed read-only
and could not have been corrupted anyway. It excludes the one context where the bug is impossible
and permits the only context where it happens.

### Standing

- Fix is a three-line deletion (`Stat.cs:63-65`), no design decision, no dependency.
- Scheduled as sprint-15 **S15-01**, "Opening block, commit 1", effort 0.05d.
- Same defect class as **BUG-077** (`HasEnoughManaCondition` writing runtime values into a committed
  condition asset), which is live *right now* and amplified 3× per cast by BUG-076 defect (c).

## Owner decision — 2026-09-22: ACCEPTED for the development phase, deferred to demo prep

The owner has ruled that `#if UNITY_EDITOR [SerializeField]` on `Stat.modifiers` (`Stat.cs:63-66`)
**stays for now**, because seeing live modifiers in the Inspector is useful while the stat system is
being built, and will be removed when the project moves from development into demo preparation.

This is a deliberate, informed trade and it supersedes every previous "one-line fix, no blocker,
carried 29+ cycles" framing in this file and in `CLAUDE.md`. The bug is not unfixed through neglect.

**Status: Open → ACCEPTED (deferred).** Not scheduled in sprint 15.

### What the acceptance costs, so the decision is re-evaluated with the facts

The leak is real while the attribute is there, and it is silent:

- Play Mode in the Editor **is** `UNITY_EDITOR`, so runtime buffs applied during a play session are
  written back into the `.asset` and marked dirty. This already happened once: two `STR +1 Flat`
  modifiers reached `PlayerStats.asset` and `Test.asset` and were **committed to git** (cleaned on
  `sprint-10`, recorded in TD-038).
- Nothing reports it. There is no warning, no log, and the diff only shows up if someone reads the
  `.asset` in a commit.

### Mitigation while the acceptance stands

Cheap, and none of them require removing the attribute:

1. **Check `git status` before committing after any Play Mode session.** A dirty
   `Assets/SO/Stat/*.asset` that you did not edit in the Inspector is the leak.
2. Consider `[NonSerialized]`-adjacent alternatives that keep the debug view without the write-back:
   a `[SerializeField] private List<StatModifier> debugView` populated in `OnValidate`, or a custom
   Inspector drawer reading `modifiers` — both show the same data and neither persists it.
3. Add the removal to the demo-prep checklist explicitly, so it is a scheduled task and not a
   remembered one. Demo-checklist item 19 in `CLAUDE.md` is the right home.

### Re-evaluation trigger

Any of: a stat `.asset` appears dirty in a commit again; the project enters demo preparation;
or a second developer joins, at which point the leak stops being one person’s known hazard.
