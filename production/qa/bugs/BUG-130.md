# BUG-130

**Title**: Dash soft-locks every class — the class animator controllers applied by `SetCharacterData()` have no Dash state, so `PlayerDashState` never gets `AnimationOnAction` / `AnimationEnd` and never exits
**Severity**: S2 (one key press — Space — freezes the player in place for the rest of the run)
**Priority**: 1 (reachable on the first Space press after a class is picked; also blocks QA cases that run after a dash)
**System**: Player state machine / Animation (class controllers)
**Found by**: Friday automated QA (`qa-auto`), QA-PLY-06.Paladin / .Archer / .Mage (inbox note NOTE-20261117-3); confirmed by the 2026-11-20 wrap-up triage
**Status**: Open — confirmed at runtime (automated Play Mode, 3 of 3 classes in 3 of 3 runs: `20261117-1646`, `20261119-1616`, `20261119-1638`) and by reading assets
**Fixed in**: —

## Description

`PlayerDashState` (`Assets/Script/Character/Player/States/PlayerDashState.cs:19-38`, added `91c42d79`)
moves the player only on `AnimationOnAction` and leaves only on `AnimationEnd`, both Animation Events
of a Dash clip. Only `Assets/AnimationController/Player/Player.controller` and
`Paladin_Dash_Skill.overrideController` contain a Dash state / `IsDash` parameter. The controllers that
`SetCharacterData()` applies after a Champion pick — `Paladin.controller`, `Archer.controller`,
`Mage.controller` under `Assets/AnimationController/Player/` — contain neither (grep at `0069a40c`).
The animator never plays a Dash clip, no event fires, and the state machine stays in `PlayerDashState`.

QA evidence: "moves 0, still in `PlayerDashState` 4 s later", every class, every run. Later cases in
the same run report "(carried over) player stuck in PlayerDashState".

The owner's working tree has an uncommitted `PlayerDashState.cs` change (invisible to the routine).

## Fix direction (owner)

Add the Dash state + `IsDash` bool (with its clips and the two events) to the three class controllers,
or give `PlayerDashState` a time-based exit that does not depend on clip events.

## How to verify

QA-PLY-06 PASS for all three classes; by hand: pick a class, press Space, the player dashes and can
move afterwards.

## Evidence added 2026-11-21 (wrap-up triage, NOTE-20261121-2)

Still KNOWN in runs `20261121-2050` / `20261121-2106` at `bcedaebb` (QA-PLY-06 x3: "moved 0, stuck in
`PlayerDashState` for 4 s"). The week's commits `8005d27e` and `67c188b3` added a second, code-side
cause and two latent defects in the same state (STATIC, `sprint-23` `68631d3f`):

1. `PlayerBasicState.cs:31-35` now checks `inputHandler.IsDash` first in `LogicUpdate()`, before
   `IsDeath`. `PlayerDashState` inherits this `LogicUpdate()` and does not override it, and `IsDash`
   stays true for `DASH_DURATION` after Space (`PlayerInputHandle.cs:310-316`). So while the flag is
   up, the dash state calls `ChangeState(player.DashState)` on itself every frame: `Exit()` nulls the
   core references (`PlayerBasicState.cs:98-105`), `Enter()` restarts the clip, and the clip never
   reaches `AnimationOnAction` / `AnimationEnd`. The old branch at `:78` is now unreachable.
   A dying player who presses Space also enters Dash before Death.
2. `PlayerDashState.cs:22,27` call `negativeReceiver.InvicisibleHurtbox()` with no null check;
   `negativeReceiver` comes from `TryGetCapability()` in `Enter()` (`:17`).
3. The hurtbox is re-enabled only in `AnimationOffAction()` (`:27`). `Exit()` (`:41-46`) does not
   re-enable it, so leaving the state between the on and off events (re-entry above, or a clip whose
   off event is missing) can leave the player with a disabled hurtbox — permanently invulnerable.
   Latent today, because BUG-135 already stops all damage.

Fix direction addition: give `PlayerDashState` its own `LogicUpdate()` (no self-transition), check
`IsDeath` before `IsDash` in `PlayerBasicState`, and call `InvicisibleHurtbox(false)` in `Exit()`.
