# BUG-070

**Title**: `VitalStatsComponent` indexes `currentStats[statType]` with no key-existence guard — same unguarded-dictionary pattern as `BUG-066`, now on the player side
**Severity**: S2 (would throw on the live player damage/heal chain for any `StatType` missing from the profile — not yet observed to fire)
**System**: Player / StatSystem
**Found by**: `pm-weekly-wrapup` code-review pass, 2026-09-13 (autonomous, `lead-programmer` agent via `/code-review`)
**Status**: Open

## Description

`Assets/Script/Character/Player/CoreComponent/VitalComponent.cs` — `GetCurrentStatValue` (line 26),
`ReceiverRecovery` (line 38), and `ReceiveReduction` (line 48) on `VitalStatsComponent` all index a
`Dictionary<StatType, float>` (`currentStats`) directly with no `TryGetValue`/`ContainsKey` guard,
seeded once from `StatHandler.GetFullStat()`. This is the exact same anti-pattern already open as
`[[BUG-066]]` on `EntityVitalStats` (the enemy-side twin of this component) — it has now propagated
to the player side that `ResourceReceiver`/`NegativeReciver` call into on every hit or pickup.

## Impact

- Any `StatType` not present in the seeded `currentStats` dictionary (e.g. a misconfigured
  `BaseStatsSO` profile, or a caller passing a `StatType` the player profile doesn't track) throws
  an unlabelled `KeyNotFoundException` on the player's damage/heal path — the mirror image of
  BUG-066's enemy-side risk.
- No EditMode test exists for either `VitalStatsComponent` or `EntityVitalStats` (TD-014) that would
  catch this before it reaches a running character.

## Suggested Fix

Same fix as BUG-066, applied here: use `TryGetValue` in all three methods, log + no-op or throw a
clear, named exception instead of the raw `KeyNotFoundException`. Recommend fixing BUG-066 and
BUG-070 together in one pass since the code shape is identical — a shared private helper
(`TryGetCurrentStat(StatType, out float)`) on a common base would prevent a third recurrence on
whichever vitals component is added next.
