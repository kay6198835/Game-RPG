# BUG-088

**Title**: `EntityMovement.SetPositionToCheck()` does not compile — `Random.range` and `trasnform.postion` do not exist
**Severity**: S1 (BUILD — the whole project fails to compile; nothing runs, no Play Mode, no Test Runner)
**Priority**: 1
**System**: Enemy AI / EntityMovement
**Found by**: Post-fetch source re-verification, 2026-09-22 (branch `origin/feature/fix-player-control`, HEAD `2a83469`)
**Status**: ⚠️ Open — PARTIAL. Both compile errors and the `Vector3`/`Vector2` defect are fixed in the working tree (uncommitted); the project builds again. **The integer division survives**: `Random.Range(10, 100)/100` is `0` for every draw, so the method assigns the entity its own position and the feature is silently dead. Severity drops S1 → S3 once the build fix is committed. *Previous status line:* Open — CONFIRMED by direct read of source

## Description

Commit `723fab1` ("coding") added a new method to
`Assets/Script/Character/Entity/CoreComponent/EntityMovement.cs:161-165`:

```csharp
public void SetPositionToCheck(Vector2 endPosition)
{
    var rangeToCheck = Random.range(0, 100)/100;
    this.endPosition = Vector3.Lerp(trasnform.postion, endPosition, rangeToCheck);
}
```

Three defects, in order of severity.

### 1. Two compile errors — BLOCKING

| Token | Problem | Compiler error |
|---|---|---|
| `Random.range` | `UnityEngine.Random` exposes `Range`, capital `R`. There is no `range` member | `CS0117: 'Random' does not contain a definition for 'range'` |
| `trasnform.postion` | Two typos in one expression. Neither `trasnform` nor `postion` exists | `CS0103: The name 'trasnform' does not exist in the current context` |

These are not "intentional typos" in the sense of the project's preserved-typo list
(`Resgister`, `attackDamege`, `Modal`, …). Those name **real, declared** members and are contracts
in serialized data. These two name **nothing** — they are ordinary slips.

**Consequence.** `Assembly-CSharp` does not build. In Unity that means: no Play Mode, no domain
reload into a working state, no Test Runner, and every other script in the project is unavailable
until this one file compiles. Every other bug in this register is unverifiable while this stands.

### 2. Integer division — the method is a no-op even after the typos are fixed

`Random.Range(0, 100)` resolves to the **`int`** overload (both arguments are `int` literals).
`int / int` is integer division, so `Random.Range(0, 100) / 100` is `0` for every draw from 0 to 99.

`var rangeToCheck` therefore infers `int` with value `0`, and `Vector3.Lerp(a, b, 0f)` returns `a`.
The method would assign the entity its own current position — the intended randomised approach point
is never produced.

Fix: `Random.Range(0f, 1f)`, or `Random.Range(0, 100) / 100f`.

### 3. `Vector3` used where the project's convention requires `Vector2`

`Vector3.Lerp` returns a `Vector3` assigned into `protected Vector2 endPosition`
(`EntityMovement.cs:11`). The implicit conversion compiles and silently truncates `z`. Every other
write to `endPosition` in this file (`:75`, `:80`, `:88`, `:156`, `:188`) is `Vector2`.
`.claude/rules/gameplay-code.md` ("Vector2 / Vector3 Convention") requires `Vector2` for gameplay
math; `Vector2.Lerp` is the correct call.

### Related, same commit — unguarded resolve in `EntityNegativeReciver`

`Assets/Script/Character/Entity/CoreComponent/EntityNegativeReciver.cs` gained a field and a call in
the same commit:

```csharp
private EntityMovement entityMovement;                 // :10
Core.GetCoreComponent(out entityMovement);             // :18, in Start()
entityMovement.SetPositionToCheck(attackPosition);     // :27, in TakeDamage()
```

`CoreBase.GetCoreComponent<T>(out …)` returns silently with `null` when nothing matches — this is
the documented hazard in `CLAUDE.md` ("Shared base layer"). `:27` dereferences the result with no
guard, on the **live enemy damage path**. Any enemy prefab without an `EntityMovement` under its
`EntityCore` will `NullReferenceException` on the first hit it takes. Guard it, or follow the
`EntityMoveState` precedent of an early return.

## Reproduction

1. Open the project in Unity 2022.3.62f3.
2. Wait for the automatic recompile.
3. Console shows `CS0117` and `CS0103` for `EntityMovement.cs:163-164`; the Play button is disabled.

Or, without the Editor: `grep -n "Random.range\|trasnform.postion" Assets/Script/Character/Entity/CoreComponent/EntityMovement.cs`

## Expected

The project compiles. `SetPositionToCheck()` biases the entity's next path target somewhere between
its current position and the attacker's position, by a random fraction in `[0, 1)`.

## Fix sketch

```csharp
public void SetPositionToCheck(Vector2 attackerPosition)
{
    float rangeToCheck = Random.Range(0f, 1f);
    endPosition = Vector2.Lerp(transform.position, attackerPosition, rangeToCheck);
}
```

The parameter is also renamed: it currently shadows the field `endPosition`, which is why the body
needs `this.` to reach the field at all. Shadowing a field with a parameter of the same name is how
the wrong one gets written six months from now.

And in `EntityNegativeReciver.TakeDamage()`:

```csharp
if (entityMovement != null) entityMovement.SetPositionToCheck(attackPosition);
```

## Notes

- **No design decision is required.** This is a mechanical fix, and it gates everything else in the
  sprint — nothing can be Play-Mode-verified until it lands.
- This is the second time a mistyped identifier has shipped to a branch tip in this project. It is
  also exactly what BUG-084 would have caught: with no `.asmdef` and no CI compile step, nothing in
  the pipeline compiles the project except a human opening the Editor.

## Owner review — 2026-09-22: compile errors fixed, **integer division is still there**

Owner position: *"t đâu thấy có issue gì"* — no issue visible.

That is now true for the part that was visible. The working tree (uncommitted) reads:

```csharp
public void SetPositionToCheck(Vector2 endPosition)
{
    var rangeToCheck = Random.Range(10, 100)/100;
    this.endPosition = Vector2.Lerp(transform.position, endPosition, rangeToCheck);
}
```

`Random.range` → `Random.Range`, `trasnform.postion` → `transform.position`, and `Vector3.Lerp` →
`Vector2.Lerp`. **Defects 1a, 1b and 3 are fixed. The file compiles.** That is why nothing is
visible: the Console is clean.

### Defect 2 survives, and it is the reason nothing is visible

```csharp
Random.Range(10, 100)   // BOTH arguments are int literals → binds Random.Range(int, int)
                        // returns an int in [10, 99]
        / 100           // int / int  →  INTEGER division
```

| `Random.Range(10, 100)` returns | `/ 100` evaluates to |
|---|---|
| 10 | 0 |
| 50 | 0 |
| 99 | 0 |

There is no draw that produces anything else: the largest possible numerator is 99, and
`99 / 100 == 0` in integer arithmetic. `var` therefore infers **`int`**, not `float`, and
`rangeToCheck` is `0` on every call, forever.

`Vector2.Lerp(a, b, 0f)` returns `a`. So the method compiles, runs, throws nothing, logs nothing,
and assigns:

```
endPosition = transform.position     // the entity's own current position
```

The enemy is told to path to where it already is. `EntityMovement.CheckNearPostion(endPosition)` is
immediately true, so the knockback-target feature does nothing at all — **silently**. This is
strictly worse than the compile error was: a compile error stops you, this does not.

### Proof without opening Unity

```csharp
// C# integer division, same rule in any compiler:
Debug.Log(Random.Range(10, 100) / 100);    // prints 0
Debug.Log(Random.Range(10, 100) / 100f);   // prints 0.1 … 0.99
```

Or check the inferred type: hover `rangeToCheck` in the IDE — it reads `int`, not `float`.

### Fix — one character

```csharp
var rangeToCheck = Random.Range(10, 100) / 100f;   // 0.10 … 0.99
```

or, clearer about intent and with no division at all:

```csharp
float rangeToCheck = Random.Range(0.1f, 1f);       // float overload, no rounding
```

Writing `float rangeToCheck` instead of `var` would also have surfaced this at compile time as
*"cannot implicitly convert int to float"* — no, in fact `int` converts to `float` implicitly, so
even that would not have caught it. Only the `100f` does.

### Two smaller items, unchanged

- **Parameter shadows the field.** `SetPositionToCheck(Vector2 endPosition)` uses the same name as
  the field `endPosition` (`:11`), which is why the body needs `this.` to reach the field.
  Renaming the parameter (`attackerPosition`) removes the trap.
- **`EntityNegativeReciver.cs:27`** still dereferences `entityMovement` with no guard:

  ```csharp
  Core.GetCoreComponent(out entityMovement);            // :18 — returns silently null on no match
  entityMovement.SetPositionToCheck(attackPosition);    // :27 — live damage path
  ```

  `CoreBase.GetCoreComponent<T>(out …)` is documented in `CLAUDE.md` as returning `null` silently.
  Any enemy prefab without an `EntityMovement` under its `EntityCore` throws on the first hit it
  takes.
